# Глава 20. Инвертированный индекс и BM25

> Проект: [`php-mini-search`](https://github.com/Researcher86/php-mini-search),
> релиз `v1.0.0`, коммит `7ecddc0`. Нужно знать: как текст превращается в термы
> (→ глава 19). Пригодится дальше: как индекс переживает падения (→ глава 18) и
> как он остаётся в согласии с базой данных (→ глава 21).

Все остальные проекты лаборатории находят данные **по ключу**: ключ в кэше,
первичный ключ в базе, диапазон в B-дереве. Поиск находит данные **по смыслу,
приблизительно**. Запрос `кабели` должен найти товар «Кабель USB-C», и самый
подходящий товар должен оказаться первым.

Отсюда два вопроса, на которые отвечает эта глава:

1. Как найти все документы, где есть все слова запроса, не читая каждый
   документ?
2. Что значит «более подходящий» в виде числа?

Ответ на первый — **инвертированный индекс**, на второй — **BM25**.

---

## 1. Проблема

Наивный поиск выглядит так: пройти по всем документам, в каждом поискать каждое
слово запроса, посчитать какую-то оценку, отсортировать. В проекте такая
реализация есть, и она даже полезна: это «оракул», с которым сверяется настоящий
индекс (см. раздел 6). Вот её суть:

```php
public function search(array $terms, int $limit, int $offset): array
{
    $terms = array_values(array_unique($terms));
    sort($terms, SORT_STRING);
    if ($terms === []) {
        return ['hits' => [], 'total' => 0];
    }

    $count = count($this->documents);
    $hits = [];

    foreach ($this->documents as $id => $fields) {
        $id = (string) $id;
        foreach ($terms as $term) {
            $found = false;
            foreach (array_keys($this->weights) as $field) {
                if (in_array($term, $fields[$field] ?? [], true)) {
                    $found = true;
                }
            }
            if (!$found) {
                continue 2;
            }
        }

        $score = 0.0;
        foreach ($terms as $term) {
            foreach ($this->weights as $field => $weight) {
                $tf = count(array_keys($fields[$field] ?? [], $term, true));
                if ($tf === 0) {
                    continue;
                }

                $df = 0;
                $total = 0;
                foreach ($this->documents as $other) {
                    $df += in_array($term, $other[$field] ?? [], true) ? 1 : 0;
                    $total += count($other[$field] ?? []);
                }
                $length = count($fields[$field] ?? []);

                $idf = log(1 + ($count - $df + 0.5) / ($df + 0.5));
                $norm = 1 - $this->b + $this->b * $length * $count / $total;
                $score += $weight * $idf * $tf * ($this->k1 + 1) / ($tf + $this->k1 * $norm);
            }
        }

        $hits[] = [$id, $score];
    }

    usort($hits, fn (array $a, array $b): int => $b[1] <=> $a[1] ?: strcmp($a[0], $b[0]));

    return ['hits' => array_slice($hits, $offset, $limit), 'total' => count($hits)];
}
```

Стоимость такого поиска растёт с размером корпуса, даже если слово встречается в

один цикл по всем документам, чтобы посчитать, насколько слово редкое. Для 40
документов в тесте это приемлемо, для 10 000 в сервисе — нет.

## 2. Устройство: индекс, вывернутый наизнанку

Обычное хранение — «документ → его слова». Инвертированный индекс хранит
обратное: **«слово → документы, в которых оно есть»**. Такой список документов
для одного терма называется **posting list**, а одна его запись — **posting**.

```text
Документы                          Инвертированный индекс (поле title)

SKU-1  "Кабель USB-C"              кабел   → { SKU-1: 1 }
SKU-2  "Адаптер USB-C на HDMI"     usb     → { SKU-1: 1, SKU-2: 1 }
SKU-3  "Зарядное устройство"       c       → { SKU-1: 1, SKU-2: 1 }
                                   адаптер → { SKU-2: 1 }
                                   hdmi    → { SKU-2: 1 }
                                   зарядн  → { SKU-3: 1 }
                                   ...
```

Число после документа — **tf** (term frequency): сколько раз терм встречается в
этом поле этого документа. Теперь вопрос «где встречается `usb`» — это одно
обращение к хеш-таблице, сколько бы документов ни было в корпусе.

### Как это выглядит в коде

Весь индекс — несколько PHP-массивов:

```php
/** @var array<string, array<string, array<int, int>>> field → term → docNum → term frequency */
private array $postings = [];

/** @var array<string, array<int, int>> field → docNum → number of terms in that field */
private array $lengths = [];

/** @var array<string, int> field → sum of the lengths of that field over all documents */
private array $totalLengths = [];

/** @var array<string, array<int, string>> field → docNum → the document's distinct terms, "\0"-joined */
private array $termsOf = [];

/** @var array<string, int> id → docNum */
private array $numbers = [];

/** @var array<int, string> docNum → id */
private array $ids = [];
```

[`src/Index/InvertedIndex.php#L40-L56`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/src/Index/InvertedIndex.php#L40-L56)

**Перевод комментариев:**
- `$postings` (`@var`): поле → терм → номер документа → частота термина.
- `$lengths` (`@var`): поле → номер документа → число терминов в этом поле.
- `$totalLengths` (`@var`): поле → сумма длин этого поля по всем документам.
- `$termsOf` (`@var`): поле → номер документа → различные термы документа,
  склеенные через `"\0"`.
- `$numbers` (`@var`): id → внутренний номер документа.
- `$ids` (`@var`): внутренний номер документа → id.

Четыре детали, которые стоит заметить:

- **Postings разделены по полям** (`title`, `body`). Так заголовку можно дать
  больший вес (раздел 4).
- **Документ хранится под внутренним номером** (`docNum`), а не под своим id.
  Строка `"SKU-1"` записана один раз в `$ids`, а в миллионах postings лежит
  маленькое целое. На 10 000 документах это заметная экономия памяти.
- **Длины полей** (`$lengths`, `$totalLengths`) нужны только для ранжирования.
  Индекс, который ничего не ранжирует, обошёлся бы без них.
- **`$termsOf`** — обратная сторона: какие термы есть у документа. Без неё
  удаление документа пришлось бы делать перебором всего словаря. О ней — в
  разделе «Удаление».

### Почему обычные массивы

Postings можно хранить компактнее, например упакованными бинарными строками
(`pack('V*', ...)`). Проект сначала **измерил** оба варианта на синтетическом
корпусе, и только потом выбрал:

| 100 000 документов | Память индекса | Байт на posting | Удаление документа |
| ------------------ | -------------- | --------------- | ------------------ |
| вложенные массивы  | 2 432 МБ       | 60              | 0,4 мс             |
| упакованные строки | 411 МБ         | 10              | 7,3 мс             |

На 100 тысячах документов массивы не помещались в бюджет памяти. Но цель проекта
— показать, как работает поиск, поэтому корпус ограничили 10 000 документов. На
таком размере массивы занимают около 300 МБ, читаются проще всего, а удаление
документа — это один `unset()` на терм. Как принималось это решение, записано в
[`docs/DECISIONS.md` → «Postings are plain PHP arrays»](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/docs/DECISIONS.md#postings-are-plain-php-arrays).

> Урок, который повторится в главе 25: структуру данных выбирают по замеру на
> целевом размере, а не «на всякий случай самую компактную».

### Добавление документа

```php
public function put(string $id, array $fields): void
{
    $unknown = array_diff_key($fields, $this->weights);
    if ($unknown !== []) {
        throw new InvalidArgumentException('Unknown field: ' . implode(', ', array_keys($unknown)));
    }

    $this->delete($id);

    $number = $this->nextNumber++;
    $this->numbers[$id] = $number;
    $this->ids[$number] = $id;

    foreach (array_keys($this->weights) as $field) {
        $terms = $fields[$field] ?? [];
        $frequencies = array_count_values($terms);

        foreach ($frequencies as $term => $tf) {
            $this->postings[$field][(string) $term][$number] = $tf;
        }

        $this->lengths[$field][$number] = count($terms);
        $this->totalLengths[$field] += count($terms);
        $this->termsOf[$field][$number] = implode("\0", array_map('strval', array_keys($frequencies)));
    }
}
```

[`src/Index/InvertedIndex.php#L81-L106`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/src/Index/InvertedIndex.php#L81-L106)

Обратите внимание:

- **Замена — это удаление и добавление** (`$this->delete($id)` в начале). Новая
  версия документа получает новый внутренний номер. Так в индексе невозможно
  случайно оставить postings старой версии: они удаляются целиком до того, как
  появятся новые.
- **`array_count_values`** превращает список термов
  `['кабел', 'usb', 'c', 'кабел']` в частоты
  `['кабел' => 2, 'usb' => 1, 'c' => 1]`. Длина поля — это число термов **с
  повторами**: 4, а не 3.
- **`(string) $term`** — защита от особенности PHP. Ключ массива `"3"` PHP
  превращает в целое `3`, и терм-число вернулся бы из `array_count_values` как
  `int`. Тест-оракул специально кладёт в словарь термы `'3'` и `'42'`, чтобы это
  поймать.

### Удаление

```php
public function delete(string $id): void
{
    $number = $this->numbers[$id] ?? null;
    if ($number === null) {
        return;
    }

    foreach (array_keys($this->weights) as $field) {
        foreach ($this->distinctTerms($field, $number) as $term) {
            unset($this->postings[$field][$term][$number]);

            if ($this->postings[$field][$term] === []) {
                unset($this->postings[$field][$term]);
            }
        }

        $this->totalLengths[$field] -= $this->lengths[$field][$number];
        unset($this->lengths[$field][$number], $this->termsOf[$field][$number]);
    }

    unset($this->numbers[$id], $this->ids[$number]);
}
```

[`src/Index/InvertedIndex.php#L108-L129`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/src/Index/InvertedIndex.php#L108-L129)

Чтобы удалить документ из postings, нужно знать, в каких списках он есть. Можно
хранить полный **прямой индекс** «документ → терм → tf», но он почти удвоил бы
память. Здесь хранится только **набор различных термов** документа, склеенный в
одну строку через `\0`. Частоты не нужны: они уже лежат в самих postings.
Разделитель `\0` безопасен, потому что термы состоят из букв и цифр и нулевого
байта в них быть не может.

Пустой posting list удаляется (`unset` при `=== []`). Иначе словарь термов рос
бы бесконечно за счёт слов, которых уже нет ни в одном документе.

## 3. Поиск: пересечение с самого редкого терма

В проекте поиск работает по семантике **AND**: документ подходит, если в нём
есть **каждое** слово запроса. Зато слова могут быть в разных полях:
`кабель usb` находит товар с «кабелем» в заголовке и «usb» в описании.

Найти документы, где есть все термы, — значит **пересечь** их posting lists.
Главный приём: начинать с **самого редкого** терма.

```php
private function matches(array $terms): iterable
{
    $bySize = [];
    foreach ($terms as $term) {
        $size = 0;
        foreach (array_keys($this->weights) as $field) {
            $size += count($this->postings[$field][$term] ?? []);
        }
        if ($size === 0) {
            return;
        }
        $bySize[$term] = $size;
    }
    asort($bySize);
    $ordered = array_map('strval', array_keys($bySize));
    $rarest = array_shift($ordered);

    $candidates = [];
    foreach (array_keys($this->weights) as $field) {
        $candidates += $this->postings[$field][$rarest] ?? [];
    }

    foreach (array_keys($candidates) as $number) {
        foreach ($ordered as $term) {
            if (!$this->contains($term, $number)) {
                continue 2;
            }
        }

        yield $number;
    }
}
```

Почему с редкого? Представьте запрос `кабель usb` в корпусе из 10 000 товаров
(числа для примера):

```text
usb    → 4 000 документов
кабел  →    30 документов

с usb:    4 000 кандидатов × проверка «есть ли кабел» = 4 000 проверок
с кабел:     30 кандидатов × проверка «есть ли usb»   =    30 проверок
```

Работа ограничена длиной **самого короткого** списка, а не корпусом и не самым
частым словом. Две мелочи в коде:

- **Ранний выход.** Если хотя бы один терм не встречается нигде (`$size === 0`),
  результат пуст, и дальше считать нечего.
- **`yield`.** Совпадения отдаются по одному, а не собираются в массив. Это
  пригодится на следующем шаге: найденные документы сразу идут в ранжирование,
  без промежуточного списка.

`contains()` проверяет терм во всех полях одним `isset` на поле:
[`src/Index/InvertedIndex.php#L307-L316`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/src/Index/InvertedIndex.php#L307-L316).

> **Цена AND.** Опечатка в одном слове даёт ноль результатов: в эксперименте
> ниже `кабель hdmi` не находит ничего, потому что ни в одном товаре нет обоих
> слов. Семантика OR вернула бы больше, но объединение списков частых термов
> дорого, и оптимизации вроде WAND/MaxScore выходят за рамки проекта. Решение и
> его цена:
> [`DECISIONS.md` → «AND, not OR»](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/docs/DECISIONS.md#and-not-or).

## 4. Ранжирование: от «встречается ли» к «насколько подходит»

Документы найдены, теперь их надо упорядочить. Интуиция, которую формализует
BM25, складывается из трёх наблюдений:

1. **Чем чаще слово встречается в документе, тем лучше** — но с насыщением.
   Документ, где «кабель» повторён 50 раз, не в 50 раз лучше документа с одним
   «кабелем». Это **tf с насыщением**, параметр `k1`.
2. **Редкое слово важнее частого.** Совпадение по `hdmi` говорит о документе
   больше, чем совпадение по `c`. Это **idf** (inverse document frequency).
3. **Одно совпадение в коротком тексте важнее, чем в длинном.** «Кабель» в
   заголовке из двух слов — сильный сигнал, в описании из ста слов — слабый. Это
   **нормализация по длине**, параметр `b`.

### Формула

```text
score(D, Q) = Σ термы t   Σ поля f   w_f · idf_f(t) · tf·(k1+1) / (tf + k1·(1 − b + b·len/avglen))

idf_f(t)    = ln(1 + (N − df_f(t) + 0.5) / (df_f(t) + 0.5))
```

- `tf` — сколько раз терм встречается в поле документа;
- `df_f(t)` — в скольких документах терм встречается в этом поле;
- `N` — число документов в корпусе;
- `len` и `avglen` — длина поля этого документа и средняя длина поля по корпусу;
- `k1 = 1.2`, `b = 0.75` — стандартные значения;
- `w_title = 2.0`, `w_body = 1.0` — вес поля.

### Код

```php
private function score(array $terms, int $number): float
{
    $documents = count($this->ids);
    $score = 0.0;

    foreach ($terms as $term) {
        foreach ($this->weights as $field => $weight) {
            $tf = $this->postings[$field][$term][$number] ?? 0;
            if ($tf === 0) {
                continue;
            }

            $df = count($this->postings[$field][$term] ?? []);
            $idf = log(1 + ($documents - $df + 0.5) / ($df + 0.5));
            $norm = 1 - $this->b + $this->b * $this->lengths[$field][$number] * $documents / $this->totalLengths[$field];

            $score += $weight * $idf * $tf * ($this->k1 + 1) / ($tf + $this->k1 * $norm);
        }
    }

    return $score;
}
```

[`src/Index/InvertedIndex.php#L321-L342`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/src/Index/InvertedIndex.php#L321-L342)

Сравните с формулой — это она же, построчно:

- **`df` не хранится отдельно.** Это просто `count()` posting list: PHP-массив
  знает свой размер за O(1). Отдельный счётчик мог бы разойтись со списком, а
  длина списка — нет.
- **`len/avglen`** записано как `len · N / totalLength`. Это то же самое
  (`avglen = totalLength / N`), но без лишнего деления.
- **Деления на ноль нет.** Если `tf > 0`, поле этого документа не пусто, значит
  `totalLengths[$field] > 0`.

### Почему idf «как в Lucene»

В учебниках часто встречается исходная формула Робертсона:
`ln((N − df + 0.5) / (df + 0.5))`. Она уходит **в минус**, когда терм есть
больше чем в половине документов. При семантике AND такой терм есть во **всех**
найденных документах, и отрицательный вклад понизил бы их все сразу. Вариант с
`1 +` под логарифмом (так считает Lucene) всегда положителен. Это закреплено
тестом
[`testATermInEveryDocumentStillScoresAboveZero`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/tests/Index/InvertedIndexTest.php#L95-L101).

### Поля и веса

Каждое поле считается отдельно, со своими `df`, длинами и весом, а результаты
складываются. Это самый простой способ дать заголовку больший вес. У него есть
известная неточность: если терм встречается и в заголовке, и в описании,
насыщение `tf` применяется к каждому полю отдельно, и терм получает почти
двойной вклад. Правильная модель — **BM25F**, где частоты сначала складываются с
весами, а насыщение применяется один раз. Её отложили: переход меняет только
формулу, а не структуру индекса.

## 5. Детерминизм: одинаковый запрос — одинаковый порядок

Две вещи легко упустить, и обе дают «плавающий» порядок результатов.

**Порядок сложения.** Сложение чисел с плавающей точкой не ассоциативно:
`(a + b) + c` может отличаться от `a + (b + c)` в последнем бите. Если
суммировать термы в том порядке, в каком их ввёл пользователь, запросы
`кабель usb` и `usb кабель` могут дать разные score, и почти равные документы
поменяются местами. Поэтому термы сначала дедуплицируются и сортируются:

```php
public function search(array $terms, int $limit, int $offset = 0): SearchResult
{
    $terms = array_values(array_unique($terms));
    sort($terms, SORT_STRING);

    if ($terms === [] || $limit < 1 || $offset < 0) {
        return new SearchResult([], 0);
    }

    $top = new TopHits($offset + $limit);
    $total = 0;

    foreach ($this->matches($terms) as $number) {
        $total++;
        $top->offer(new SearchHit($this->ids[$number], $this->score($terms, $number)));
    }

    return new SearchResult(array_slice($top->best(), $offset), $total);
}
```

[`src/Index/InvertedIndex.php#L183-L201`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/src/Index/InvertedIndex.php#L183-L201)

**Равные score.** При равенстве нужен фиксированный порядок, иначе он зависит от
порядка вставки в хеш-таблицу. Здесь при равном score выше оказывается меньший
id:

```php
private static function better(SearchHit $a, SearchHit $b): bool
{
    if ($a->score !== $b->score) {
        return $a->score > $b->score;
    }

    return strcmp($a->id, $b->id) < 0;
}
```

[`src/Index/TopHits.php#L71-L78`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/src/Index/TopHits.php#L71-L78)

### Top-k вместо сортировки всего

Запрос просит 10 результатов, а совпадений может быть несколько тысяч.
Сортировать все — `O(n log n)`. `TopHits` держит **кучу размера k**
(`offset + limit`), на вершине которой лежит **худший** из хранимых результатов.
Новый документ попадает в кучу, только если он лучше этого худшего:

```php
public function offer(SearchHit $hit): void
{
    if ($this->count() < $this->capacity) {
        $this->insert($hit);

        return;
    }

    if ($this->capacity > 0 && self::better($hit, $this->top())) {
        $this->extract();
        $this->insert($hit);
    }
}
```

[`src/Index/TopHits.php#L28-L40`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/src/Index/TopHits.php#L28-L40)

Стоимость — `O(n log k)`, а память — `k` элементов вместо `n`. Отсюда и лимит
глубины в API: `offset + limit ≤ 1000`. Страница на глубине `offset` требует
держать в куче `offset + limit` документов.

`total` при этом точный: это просто счётчик совпадений, который увеличивается в
цикле, даже если документ в кучу не попал.

## 6. Эксперимент

Соберите маленький индекс из трёх товаров и посмотрите на числа. Внутри
контейнера `php-mini-search` (`make shell`) создайте файл `exp.php`:

```php
<?php
require 'vendor/autoload.php';

use PhpMiniSearch\Analysis\Analyzer;
use PhpMiniSearch\Index\InvertedIndex;

$analyzer = new Analyzer();
$index = new InvertedIndex();

$products = [
    'SKU-1' => ['Кабель USB-C', 'Быстрая зарядка, длина 2 метра'],
    'SKU-2' => ['Адаптер USB-C на HDMI', 'Подключите ноутбук к монитору'],
    'SKU-3' => ['Зарядное устройство', 'Кабель USB-C в комплекте, быстрая зарядка'],
];
foreach ($products as $sku => [$title, $body]) {
    $index->put($sku, ['title' => $analyzer->terms($title), 'body' => $analyzer->terms($body)]);
}

foreach (['кабели', 'usb', 'быстрая зарядка', 'кабель hdmi'] as $query) {
    $result = $index->search($analyzer->terms($query), 10);
    printf("%-18s total=%d", $query, $result->total);
    foreach ($result->hits as $hit) {
        printf("  %s=%.4f", $hit->id, $hit->score);
    }
    echo "\n";
}

echo "\n", json_encode($index->describe('SKU-3'), JSON_UNESCAPED_UNICODE), "\n";
```

и запустите `php exp.php`:

```text
кабели       total=2  SKU-1=2.0453  SKU-3=0.8697
usb                total=3  SKU-1=0.9801  SKU-3=0.8697  SKU-2=0.7804
быстрая зарядка total=2  SKU-1=0.9647  SKU-3=0.8335
кабель hdmi  total=0

{"title":{"length":2,"terms":{"зарядн":1,"устройств":1}},"body":{"length":7,"terms":{"кабел":1,"usb":1,"c":1,"в":1,"комплект":1,"быстр":1,"зарядк":1}}}
```

(Колонки «съехали», потому что `printf` считает байты, а кириллица в UTF-8
занимает два байта на букву.)

Что здесь видно:

- **`кабели` нашёл «Кабель».** Запрос и документ прошли через один и тот же
  анализатор и превратились в один терм `кабел` (→ глава 19).
- **SKU-1 сильно выше SKU-3**: у SKU-1 «кабель» в заголовке (вес 2,0) из трёх
  слов, у SKU-3 — в описании из семи.
- **`кабель hdmi` ничего не нашёл.** Это AND в действии: ни в одном товаре нет
  обоих слов.
- **`быстрая зарядка`: SKU-1 выше SKU-3**, хотя оба нашлись по описанию.
  Описание SKU-1 короче (5 термов против 7), нормализация по длине поднимает
  его.

### Посчитаем один score вручную

Запрос `кабели`, документ SKU-1. Терм `кабел` встречается в заголовке SKU-1 один
раз (`tf = 1`). Он есть в заголовке только одного документа (`df_title = 1`),
документов три (`N = 3`). Длины заголовков: SKU-1 — 3 (`кабел usb c`), SKU-2 —
5, SKU-3 — 2. Значит, `avglen = 10 / 3 ≈ 3,333`.

```text
idf   = ln(1 + (3 − 1 + 0.5) / (1 + 0.5))      = ln(2.6667)        = 0.9808
norm  = 1 − 0.75 + 0.75 · 3 / 3.333             = 0.25 + 0.675      = 0.925
tf'   = 1 · (1.2 + 1) / (1 + 1.2 · 0.925)       = 2.2 / 2.11        = 1.0427
score = 2.0 (вес title) · 0.9808 · 1.0427                           = 2.0453
```

Совпадает с выводом программы.

### Неожиданный результат: `usb`

По запросу `usb` товар SKU-3, у которого слово стоит **в описании**, оказался
**выше** SKU-2, у которого оно **в заголовке** с весом 2,0. Как так?

Потому что idf считается **отдельно для каждого поля**. В заголовках `usb`
встречается дважды (SKU-1 и SKU-2), а в описаниях — один раз (SKU-3). В поле
`body` слово «реже», значит его idf больше:

```text
SKU-2, title:  idf = ln(1 + 1.5/2.5) = 0.470   норм. по длине 5/3.33   → 2.0 · 0.470 · 0.830 = 0.7804
SKU-3, body:   idf = ln(1 + 2.5/1.5) = 0.981   норм. по длине 7/5.33   → 1.0 · 0.981 · 0.887 = 0.8697
```

На трёх документах эффект преувеличен. На реальном корпусе статистика поля
устойчивее, и вес заголовка работает как ожидается: это проверяет тест
[`testATitleMatchOutranksTheSameMatchInTheBody`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/tests/Index/InvertedIndexTest.php#L70-L76).
Но урок общий: **ранжирование зависит от статистики корпуса**, и один и тот же
документ на одном и том же запросе может получить разное место в разных
корпусах.

## 7. Отказы

Что здесь может сломаться, и что этому мешает:

| Что ломается                                  | Чем это проявится                                   | Что мешает                                                                             |
| --------------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------- |
| При замене документа остались старые postings | документ находится по словам, которых в нём уже нет | замена = удаление + добавление; инвариант «каждый posting указывает на живой документ» |
| Счётчики длин разошлись с postings            | неверный BM25 у всех документов                     | `df` не хранится отдельно, а `totalLengths` проверяется инвариантом                    |
| Порядок равных score зависит от вставки       | «прыгающие» результаты между запросами              | тай-брейк по id в `TopHits::better()`                                                  |
| Порядок слов запроса меняет score             | `кабель usb` и `usb кабель` ранжируются по-разному  | термы сортируются перед суммированием                                                  |
| Терм-число стал ключом-int                    | термы `3` и `42` теряются или не находятся          | `(string) $term` и такие термы в словаре теста                                         |

Индекс живёт только в памяти. Как он восстанавливается после падения процесса,
разбирается в главе 18.

## 8. Как это проверено

Писать тесты на ранжирование вручную («документ А должен быть выше B») полезно,
но они ловят только то, о чём автор подумал. Поэтому основной тест индекса
устроен иначе: он сравнивает индекс с **оракулом**.

**Оракул** — та самая наивная реализация из раздела 1. Она считает BM25 прямо по
формуле, заново на каждый запрос, без единой оптимизации. В ней негде спрятаться
ошибкам индекса: нет postings, нет кэшей длин, нет кучи.

Тест
[`InvertedIndexAgainstOracleTest`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/tests/Index/InvertedIndexAgainstOracleTest.php)
делает 5 × 2 500 случайных операций (добавить, заменить, удалить, найти) и
выполняет каждую параллельно на индексе и на оракуле. Результаты должны
совпадать: те же id, в том же порядке, score с точностью до `1e-9`. После
**каждой** операции индекс проверяет свои инварианты
([`invariantViolations()`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/src/Index/InvertedIndex.php#L203-L265)).

### А тест вообще способен упасть?

Тест, который ничего не ловит, хуже, чем отсутствие теста: он даёт ложную
уверенность. Поэтому его проверили **мутациями**: в индекс по одной вносили
намеренные ошибки и смотрели, упадёт ли тест.

| Внесённая ошибка                           | Результат          |
| ------------------------------------------ | ------------------ |
| при замене документа postings не удаляются | пойман на 6-м шаге |
| `N` в формуле idf на единицу больше        | пойман на 4-м шаге |
| тай-брейк перевёрнут (больший id выше)     | **не пойман**      |

Третья ошибка прошла, и причина поучительная. Случайные документы почти никогда
не получают побитово равный score, поэтому тай-брейк просто не срабатывал. После
этого генератор начал в четверти случаев записывать **точную копию** ранее
записанного документа под новым id, а тест — требовать больше 100 равенств score
за прогон. Перевёрнутый тай-брейк стал ловиться на 20-м шаге. Подробно этот
приём разобран в главе 26.

Замеры на этом коде
([`docs/BENCHMARKS.md`](https://github.com/Researcher86/php-mini-search/blob/7ecddc0278acc5e4ac22098c7d9aa5ebebe86ef3/docs/BENCHMARKS.md)):

|                                | Синтетика, 10 000 док. | Википедия, 10 000 статей |
| ------------------------------ | ---------------------- | ------------------------ |
| термов в словаре               | 25 896                 | 151 505                  |
| поиск, запросов в секунду      | 489                    | 10 575                   |
| поиск, p50 под 16 соединениями | 32 мс                  | 1 мс                     |

Код один и тот же, а скорость отличается в 22 раза. Всё объясняет раздел 3. В
синтетическом корпусе мало термов и очень крутое распределение, поэтому частые
термы есть почти в каждом документе, а самый редкий терм запроса всё равно
«частый». Пересечение начинается со списка в тысячи документов, и для каждого
считается BM25. В Википедии слова из заголовков редкие, списки короткие, работы
мало.

Отсюда практический вывод: **производительность поиска определяется
распределением термов в корпусе**, а не только числом документов. Худший случай
— запрос из одних частых слов.

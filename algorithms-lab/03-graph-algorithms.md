# Глава 3. Графы: представление — это бюджет памяти

> Проект: [`algorithms-lab`](https://github.com/Researcher86/algorithms-lab),
> тег [`v1.0.0`](https://github.com/Researcher86/algorithms-lab/releases/tag/v1.0.0).
> Предыдущая глава: [LRU и LFU](02-lru-lfu-cache.md).
> Дальше: B-дерево (глава 4).

Один и тот же граф можно загрузить в четыре структуры, и все четыре дадут
одинаковый ответ BFS. Но память, время построения и число чтений будут
разными. В этой главе граф — это не абстрактная пара `(V, E)`, а конкретный
бюджет: матрица смежности платит `V²` даже за четыре тысячи рёбер, а CSR
укладывает те же рёбра в два плоских массива.

Вторая тема — счётчики. BFS и DFS должны прочитать каждую дугу ровно один
раз, Dijkstra с ленивой кучей может извлечь больше вершин, чем в графе, а
naive union-find на плохой цепочке делает девять тысяч чтений на один find.
Эти числа проверяют сложность лучше, чем один шумный замер времени.

---

## 1. Проблема

Граф нужен, когда связи важнее самих объектов: маршруты, зависимости,
социальные связи, ссылки между страницами. Первое решение при проектировании
— как хранить рёбра. От него зависят:

- сколько памяти займёт граф;
- как быстро добавить ребро;
- как быстро получить соседей вершины;
- можно ли проверить наличие ребра за `O(1)`;
- сколько стоит обойти весь граф.

Для разреженного графа с `E << V²` матрица смежности — расточительство. Для
плотного графа она может быть удобна. Список рёбер хорош для алгоритмов,
которые один раз сортируют рёбра (Kruskal), но плох для частых запросов
соседей. CSR — это компромисс: после построения он компактен и быстро
перебирает соседей, но не поддерживает дешёвую вставку.

Вторая проблема — алгоритмы. BFS и DFS дают обход за `O(V + E)`. Dijkstra
требует неотрицательных весов и кучи. Bellman-Ford терпит отрицательные
рёбра и умеет находить отрицательный цикл. Union-find отвечает на вопрос о
компонентах связности, но его amortized-граница не означает, что каждая
операция дешёвая.

## 2. Устройство

### 2.1. AdjacencyList

`AdjacencyList` хранит массив `adjacency`, где `adjacency[v]` — map
`сосед => вес`. Для неориентированного ребра добавляются две записи, для
петли — одна. Проверка `array_key_exists` не даёт дважды увеличить
`edgeCount` при повторной вставке того же ребра.

```php
    public function addEdge(int $from, int $to, float $weight = 1.0): void
    {
        $this->assertVertex($from);
        $this->assertVertex($to);
        $this->assertWeight($weight);

        if ($this->directed) {
            if (!array_key_exists($to, $this->adjacency[$from])) {
                ++$this->edgeCount;
            }

            $this->adjacency[$from][$to] = $weight;

            return;
        }

        if (!array_key_exists($to, $this->adjacency[$from])) {
            ++$this->edgeCount;
        }

        $this->adjacency[$from][$to] = $weight;

        if ($from !== $to) {
            $this->adjacency[$to][$from] = $weight;
        }
    }
```

[`src/Graph/AdjacencyList.php` L35-L60](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/Graph/AdjacencyList.php#L35-L60)

Память — `O(V + E)`, перебор соседей — `O(deg(v))`, проверка ребра — в
среднем `O(1)`. Внутренний map даёт больше, чем чистый список: он умеет
быстро отвечать `hasEdge`, но платит за это хеш-таблицей на каждую вершину.

### 2.2. Matrix, EdgeList, CSR

`AdjacencyMatrix` хранит `V × V` ячеек. Добавление и проверка ребра — `O(1)`,
но память — `O(V²)`, независимо от `E`. При `V = 1 000` и `E = 4 000` это
16.0 MiB против 527.3 KiB у списка.

`EdgeList` хранит плоский список рёбер. Он компактен в памяти, но
`addEdge()` сканирует список, чтобы не дублировать ребро; на 4 000 рёбер это
101.9 ms построения. Такой вариант хорош для Kruskal, где рёбра всё равно
сортируются, и плох для интерактивного добавления.

`CsrGraph` строится из списка рёбер один раз: считает степени, строит
`offsets`, затем заполняет `targets` и `weights`. Память — `O(V + E)`,
перебор соседей — по срезу `offsets[v]..offsets[v+1]`. Вставка после
построения не поддерживается; это цена компактности.

### 2.3. BFS и очередь без `array_shift`

BFS хранит очередь как PHP list и индекс `head`. Если использовать
`array_shift()`, каждый сдвиг переиндексирует массив и превращает обход в
`O(V²)` на большой очереди. Здесь `head` просто увеличивается, а список
растёт в конец.

```php
    public static function run(Graph $graph, int $source, ?Counters $counters = null): BfsResult
    {
        self::assertSource($graph, $source);
        $distances = array_fill(0, $graph->vertexCount(), -1);
        $parents = array_fill(0, $graph->vertexCount(), null);
        $order = [];
        $queue = [$source];
        $head = 0;
        $distances[$source] = 0;

        while ($head < count($queue)) {
            $vertex = $queue[$head];
            ++$head;
            $order[] = $vertex;

            foreach ($graph->neighbors($vertex) as $neighbor => $weight) {
                if ($counters !== null) {
                    ++$counters->nodeReads;
                }

                if ($distances[$neighbor] !== -1) {
                    continue;
                }

                $distances[$neighbor] = $distances[$vertex] + 1;
                $parents[$neighbor] = $vertex;
                $queue[] = $neighbor;
            }
        }

        return new BfsResult($order, $distances, $parents);
```

[`src/Graph/Bfs.php` L19-L49](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/Graph/Bfs.php#L19-L49)

Счётчик `nodeReads` увеличивается на каждой прочитанной дуге. Для
неориентированного графа каждая дуга читается из обоих концов, поэтому
ожидаемое число — `2E`. Это прямой тест на `O(V + E)`, не зависящий от
времени.

### 2.4. Dijkstra с ленивой кучей

`Dijkstra` хранит расстояния, родителей и флаг `settled`. При улучшении
расстояния он не уменьшает ключ в куче, а вставляет новую запись. Старая
запись останется в куче, пока не будет извлечена; тогда её расстояние
сравнивается с текущим и устаревшая запись пропускается.

```php
        while (!$heap->isEmpty()) {
            $entry = $heap->extract();
            ++$heapPops;

            if ($counters !== null) {
                ++$counters->nodeReads;
            }

            if (!$entry instanceof DijkstraEntry) {
                throw new LogicException('Dijkstra heap contains a non-entry');
            }

            if ($settled[$entry->vertex]) {
                continue;
            }

            if ($entry->distance > $distances[$entry->vertex]) {
                continue;
            }

            $settled[$entry->vertex] = true;

            foreach ($graph->neighbors($entry->vertex) as $neighbor => $weight) {
                $candidate = $distances[$entry->vertex] + $weight;

                if ($candidate >= $distances[$neighbor]) {
                    continue;
                }

                $distances[$neighbor] = $candidate;
                $parents[$neighbor] = $entry->vertex;
                ++$relaxations;
                $heap->insert(new DijkstraEntry($neighbor, $candidate));
            }
        }

        return new ShortestPaths($distances, $parents, $relaxations, $heapPops);
```

[`src/Graph/Dijkstra.php` L50-L86](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/Graph/Dijkstra.php#L50-L86)

Такая схема проще decrease-key: не нужен map позиций и операция уменьшения
ключа. Цена — лишние извлечения. На 500 вершинах и 2 000 рёбрах ленивая куча
извлекла 894 записи, а decrease-key-вариант — ровно 500. Обе версии дали
одинаковое расстояние до вершины 499: 140.00.

Дополнительно в лаборатории есть:

- `DijkstraDecreaseKey` с индексированной кучей;
- `BellmanFord` с флагом отрицательного цикла;
- `TopologicalSort` (Kahn и DFS);
- `UnionFind` с compression + rank, compression-only, rank-only и naive;
- `Kruskal` и `Prim` для минимального остовного дерева.

## 3. Эксперимент

Граф генерируется один раз, затем загружается в каждое представление.
Абсолютное время шумное; число чтений и память устойчивее.

```bash
make experiment ARGS="graph:representations --seed=book"
```

1 000 вершин, 4 000 неориентированных взвешенных рёбер, BFS из вершины 0:

| представление | PHP memory | bytes/vertex | build | BFS seen |
|---|---:|---:|---:|---:|
| AdjacencyList | 527.3 KiB | 540.0 | 1.433 ms | 999 |
| AdjacencyMatrix | 16.0 MiB | 16 795.2 | 2.401 ms | 999 |
| EdgeList | 455.5 KiB | 466.5 | 101.907 ms | 999 |
| CsrGraph | 303.1 KiB | 310.4 | 1.758 ms | 999 |

В графе есть одна изолированная вершина, поэтому BFS видит 999 из 1 000.
Матрица платит за `V²` ячеек, хотя рёбер всего 4 000. CSR меньше списка,
потому что не хранит map на каждую вершину. EdgeList компактен, но его
построение квадратично из-за проверки дубликатов.

Обходы:

| graph | V | E | BFS | DFS | BFS max distance | components | neighbour reads |
|---|---:|---:|---:|---:|---:|---:|---:|
| sparse | 1 000 | 3 000 | 0.473 ms | 0.932 ms | 7 | 3 | 6 000 |
| denser | 1 000 | 8 000 | 0.457 ms | 1.618 ms | 4 | 1 | 16 000 |

Оба обхода читают ровно `2E` дуг: 6 000 и 16 000. Это и есть проверка
`O(V + E)`. DFS в PHP медленнее из-за стека enter/exit и `array_keys()` на
каждой вершине; это константа, а не другой класс сложности.

Dijkstra, 500 вершин, 2 000 рёбер, веса 1–100:

| algorithm | time | relaxations | heap pops | node reads |
|---|---:|---:|---:|---:|
| lazy binary heap | 4.289 ms | 893 | 894 | 894 |
| indexed heap, decrease-key | 2.142 ms | 893 | 500 | 500 |
| SplPriorityQueue | 0.720 ms | 888 | 889 | 0 |
| Bellman-Ford | 3.881 ms | 2 068 | 0 | 0 |

Ленивая куча извлекла 894 записи на 500 вершин: 394 лишние записи — это
устаревшие улучшения. Decrease-key держит в куче не больше `V`. C-level
`SplPriorityQueue` быстрее, но его сравнения не инструментированы; это
языковой baseline, а не доказательство лучшей асимптотики.

Union-find, 10 000 элементов и 1 000 find после специально глубокой цепочки:

| variant | time | node reads/find | total reads |
|---|---:|---:|---:|
| compression + rank | 0.123 ms | 1.00 | 1 000 |
| compression only | 1.213 ms | 20.996 | 20 996 |
| rank only | 0.103 ms | 1.00 | 1 000 |
| naive | 472.805 ms | 9 999.00 | 9 999 000 |

Compression-only доминируется первым find, который проходит и переписывает
всю цепочку; следующие find дешёвые, поэтому среднее 21. Rank-only держит
цепочку мелкой. Naive платит полный путь каждый раз. Это наглядный пример
amortized-границы: одна дорогая операция может окупиться последующими.

## 4. Что ломается

**Матрица на разреженном графе.** 16.0 MiB против 527.3 KiB — это не
«немного больше». При `V = 100 000` матрица невозможна, даже если рёбер
сотни тысяч. Выбор представления — это выбор предела роста.

**EdgeList и вставка.** Построение 101.9 ms на 4 000 рёбер показывает, что
`addEdge()` со сканированием — это `O(E)` на операцию. Для Kruskal это
нормально, для потока событий — нет.

**Ленивая куча Dijkstra.** Она проще, но может извлечь больше записей, чем
вершин. На больших графах это заметно. Decrease-key требует map позиций и
аккуратной реализации; `SplPriorityQueue` не даёт его бесплатно.

**DFS не всегда быстрее BFS.** В этом PHP-коде итеративный DFS хранит
enter/exit-фреймы и вызывает `array_keys()`; константа хуже. Сложность
одинаковая, но production-выбор зависит от констант и памяти стека.

**C-level baseline.** `SplPriorityQueue` и `Kruskal` против PHP `Prim` — это
сравнение реализаций, а не универсальный рейтинг алгоритмов. Kruskal
выигрывает здесь потому, что сортирует 2 000 рёбер и делает почти линейный
union-find, а Prim гоняет PHP-кучу.

**Отрицательные рёбра.** Dijkstra их отвергает исключением. Для них нужен
Bellman-Ford, который возвращает флаг отрицательного цикла, а не молча
выдаёт неправильные расстояния.

## 5. Как это проверено

Тесты сравнивают BFS/DFS с эталонным обходом на случайных графах, проверяют
изолированные вершины, петли, дубликаты рёбер, направленные и
неориентированные варианты. Для Dijkstra есть дифференциальный тест против
Bellman-Ford на графах без отрицательных рёбер и проверка отказа на
отрицательном весе. Для union-find — сравнение с наивной моделью и проверка
компонент после объединений.

Счётчики `nodeReads`, `relaxations`, `heapPops` и `comparisons` — это
контрактные проверки: `2E` для обхода, `V` для decrease-key, `9999` чтений
naive-цепочки. Они не зависят от скорости хоста. `make check` дополнительно
запускает PHPStan и форматтер.

## 6. Что запомнить

- Представление графа — это прежде всего бюджет памяти: `O(V²)` против
  `O(V + E)`.
- BFS/DFS читают каждую дугу; для неориентированного графа это `2E`.
- Ленивая куча Dijkstra проще, но может извлечь больше `V` записей;
  decrease-key ограничивает кучу.
- `SplPriorityQueue` — полезный C-baseline, но не замена измеренной
  реализации.
- Union-find с rank и compression даёт почти константу; naive на плохой
  цепочке — `O(V)` на find.
- A*, Tarjan SCC, PageRank и Barabási–Albert не реализованы; глава о них
  ничего не утверждает.

   раскрытых вершин и почему?
4. Проверьте Bellman-Ford на отрицательном цикле. Как отличить «нет пути»
   от «расстояние бесконечно»?
5. Сравните Kruskal и Prim на плотном и разреженном графе. Объясните, почему
   результат зависит от реализации кучи.

## 8. Что дальше

Графы отвечают на вопрос о связях. B-дерево отвечает на вопрос о порядке:
как хранить миллионы ключей так, чтобы поиск и диапазонный запрос стоили
немного обращений к страницам. Следующая глава строит B-дерево и B+ дерево,
а затем отделяет модель страниц от реального page cache.

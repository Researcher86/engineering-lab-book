# Глава 1. Hash table и Bloom filter: загрузка, пробы и ложные срабатывания

> Проект: [`algorithms-lab`](https://github.com/Researcher86/algorithms-lab),
> тег [`v1.0.0`](https://github.com/Researcher86/algorithms-lab/releases/tag/v1.0.0).
> Это первая глава. Дальше: LRU/LFU (глава 2).

В PHP массив уже является хеш-таблицей. Поэтому «написать хеш-таблицу» в
учебных целях легко, а понять, где именно расходуется память и почему при
высокой загрузке всё разваливается, — труднее. В этой главе две структуры:
обычная хеш-таблица с разными стратегиями разрешения коллизий и Bloom filter,
который отвечает «возможно, есть» и никогда не даёт ложных отрицаний.

Глава отвечает на два вопроса. Первый: как load factor `α = n / capacity`
меняет число проб, а не только формальную сложность. Второй: что именно
обещает Bloom filter, если он не хранит ключи и не умеет удалять элементы.

---

## 1. Проблема

Хеш-таблица нужна, когда по ключу надо быстро получить значение: найти
сессию, проверить наличие URL, сопоставить идентификатор с записью. В
идеальном мире хеш-функция разводит ключи по разным ячейкам, и операция
занимает `O(1)`. В реальном мире ключей больше, чем ячеек, и хеш-функция
конечна: возникают коллизии. Способ их разрешения — это и есть выбор
структуры.

Есть два базовых семейства:

- **separate chaining**: в каждой ячейке лежит список элементов; коллизия
  просто добавляет ещё один элемент;
- **open addressing**: все элементы лежат в самом массиве; коллизия ищет
  следующую свободную ячейку по некоторой последовательности проб.

У обоих есть цена. Chaining платит за указатели и объект на каждый ключ, но
не заполняет таблицу «до отказа» и легко удаляет элементы. Open addressing
не платит за отдельный объект, зато при `α`, близком к единице, промах
превращается в долгую прогулку по занятым ячейкам. Удаление требует
надгробий (`TOMBSTONE`), иначе поиск может остановиться раньше времени.

Bloom filter решает другую задачу. Он не хранит значения и даже не хранит
ключи: это битовый массив и несколько хеш-функций. `add(key)` ставит `k`
битов, `mightContain(key)` проверяет их. Если хотя бы один бит равен нулю,
ключа точно нет. Если все биты равны единице, ключ, возможно, есть: биты
могли быть поставлены другими ключами. Это **ложноположительное
срабатывание**, и оно является платой за компактность.

Bloom полезен как фильтр перед дорогим поиском: «сначала спроси Bloom, потом
иди на диск». Он не заменяет точную таблицу и не подходит для удаления
элементов. В интеграционном сценарии главы 7 он используется именно как
детектор первого появления URL, а не как источник истины.

## 2. Устройство

### 2.1. Separate chaining

В `ChainingHashTable` массив `buckets` хранит списки объектов `Entry`. При
вставке мы считаем индекс, проходим по списку и либо заменяем значение
существующего ключа, либо добавляем новый элемент. Если список непустой,
счётчик коллизий увеличивается. После вставки проверяется load factor, и
таблица при необходимости растёт.

```php
    public function put(string $key, mixed $value): void
    {
        $index = $this->indexFor($key);

        foreach ($this->buckets[$index] as $position => $entry) {
            ++$this->counters->comparisons;

            if ($entry->key === $key) {
                $this->buckets[$index][$position] = new Entry($key, $value);

                return;
            }
        }

        if ($this->buckets[$index] !== []) {
            ++$this->counters->collisions;
        }

        $this->buckets[$index][] = new Entry($key, $value);
        ++$this->size;

        if ($this->autoResize && $this->loadFactor() > $this->maxLoadFactor) {
            $this->resize($this->capacity * 2);
        }
    }
```

[`src/HashTable/ChainingHashTable.php` L56-L80](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/HashTable/ChainingHashTable.php#L56-L80)

Здесь важны две вещи. Во-первых, поиск существующего ключа в среднем
просматривает `1 + α/2` элемента, а промах — примерно `α`: при `α = 0.5`
это дёшево, при `α = 0.9` уже заметно. Во-вторых, рост таблицы — это
`rehash`: все старые элементы нужно разложить заново. Вставка в обычном
случае `O(1)`, но отдельная вставка, вызвавшая рост, стоит `O(n)`.

### 2.2. Open addressing

`OpenAddressingHashTable` хранит три параллельных массива: ключи, значения
и состояния ячеек. В ячейке может быть `EMPTY`, `OCCUPIED` или `TOMBSTONE`.
Поиск начинается с `hash % capacity` и идёт по последовательности проб, пока
не найдёт ключ, не увидит пустую ячейку или не обойдёт всю таблицу.

```php
    private function findSlot(string $key, bool $forInsert): int
    {
        ++$this->counters->hashCalls;
        $hash = $this->hashFunction->hash($key);
        $start = $hash % $this->capacity;
        $step = $this->stepFor($hash);
        $firstTombstone = -1;

        for ($probe = 0; $probe < $this->capacity; ++$probe) {
            $index = $this->slotFor($start, $probe, $step);
            ++$this->counters->probes;
            $state = $this->states[$index];

            if ($state === self::OCCUPIED) {
                ++$this->counters->comparisons;

                if ($this->keys[$index] === $key) {
                    return $index;
                }

                continue;
            }

            if ($state === self::TOMBSTONE) {
                if ($forInsert && $firstTombstone < 0) {
                    $firstTombstone = $index;
                }

                continue;
            }

            return $forInsert ? ($firstTombstone >= 0 ? $firstTombstone : $index) : -1;
        }

        return $forInsert ? $firstTombstone : -1;
    }
```

[`src/HashTable/OpenAddressingHashTable.php` L220-L255](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/HashTable/OpenAddressingHashTable.php#L220-L255)

Стратегия проб задаётся в `slotFor()`:

- линейная: `(start + probe) % capacity`;
- квадратичная: `(start + probe * (probe + 1) / 2) % capacity`;
- двойное хеширование: `(start + probe * step) % capacity`.

Линейные пробы создают **primary clustering**: занятые ячейки слипаются в
длинные серии, и промах идёт по всей серии. Квадратичные и двойные пробы
распределяют серии лучше, но всё равно деградируют при высокой загрузке.
Надгробие позволяет удалить элемент, не разрывая цепочку поиска, но
занимает ячейку до следующего rehash. Поэтому `put()` считает
`size + tombstones` и может вырасти раньше, чем `size` достигнет порога.

### 2.3. Bloom filter

Bloom filter выбирает размер битового массива `m` и число хешей `k` из
ожидаемого числа элементов `n` и целевой вероятности `p`:

```text
m = -n ln(p) / (ln 2)^2
k = (m / n) ln 2
```

В коде эти формулы вынесены в статические методы, а конструктор сохраняет
ожидаемое число элементов и целевую вероятность.

```php
    public static function optimalBits(int $expectedItems, float $falsePositiveRate): int
    {
        if ($expectedItems < 1 || $falsePositiveRate <= 0.0 || $falsePositiveRate >= 1.0) {
            throw new InvalidArgumentException('Need a positive item count and a rate in (0, 1)');
        }

        $bits = -($expectedItems * log($falsePositiveRate)) / (log(2.0) ** 2);

        return max(1, (int) ceil($bits));
    }

    public static function optimalHashCount(int $bitCount, int $expectedItems): int
    {
        if ($bitCount < 1 || $expectedItems < 1) {
            throw new InvalidArgumentException('Bit and item counts must be positive');
        }

        return max(1, (int) round(($bitCount / $expectedItems) * log(2.0)));
    }
```

[`src/BloomFilter/BloomFilter.php` L56-L74](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/BloomFilter/BloomFilter.php#L56-L74)

`add()` ставит `k` битов, а `mightContain()` проверяет их. Позиции
получаются двойным хешированием: два независимых хеша дают стартовую
позицию и шаг, а остальные позиции — это арифметическая прогрессия по модулю
`m`. Это дешевле, чем считать `k` независимых хешей.

```php
    public function add(string $key): void
    {
        ++$this->inserted;

        foreach ($this->positions($key) as $position) {
            ++$this->counters->probes;
            $this->bits->set($position);
        }
    }

    public function mightContain(string $key): bool
    {
        foreach ($this->positions($key) as $position) {
            ++$this->counters->probes;

            if (!$this->bits->get($position)) {
                return false;
            }
        }

        return true;
    }
```

[`src/BloomFilter/BloomFilter.php` L76-L97](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/BloomFilter/BloomFilter.php#L76-L97)

У Bloom нет операции `remove()`. Если сбросить бит, который поставил другой
ключ, этот другой ключ станет ложноотрицательным. Для удаления нужен
Counting Bloom или другой вариант с счётчиками, и тогда компактность
уменьшается. `inserted` считает вставки, а `estimatedFalsePositiveRate()`
пересчитывает вероятность по фактическому заполнению, а не по исходной
цели. Эти три числа — цель, оценка и измерение — нельзя смешивать.

## 3. Эксперимент

Все команды запускаются внутри Docker-контейнера проекта. На хосте нужен
только Docker; PHP, расширения и зависимости уже есть в образе.

```bash
make experiment ARGS="hash:load-factor --elements=20000 --seed=book"
```

Эксперимент вставляет один и тот же набор ключей в четыре представления при
заданном `α` и измеряет среднее число проб на попадание и промах. Числа ниже
сняты в Docker на macOS; среда печатается самим harness:

```text
PHP 8.5.11 on Linux 7.0.14-linuxkit, aarch64 x 12, memory_limit 512M, cgroup unlimited
OPcache off, JIT off, Xdebug off, allocator Zend MM
```

| α | элементов | chaining hit/miss | linear hit/miss | quadratic hit/miss | double hit/miss |
|---:|---:|---:|---:|---:|---:|
| 0.50 | 16 384 | 1.315 / 0.473 | 1.769 / 2.642 | 1.588 / 2.158 | 1.453 / 1.976 |
| 0.75 | 12 288 | 1.485 / 0.740 | 3.159 / 8.334 | 2.296 / 4.649 | 1.975 / 3.934 |
| 0.90 | 14 745 | 1.634 / 0.856 | 9.928 / 116.095 | 3.620 / 15.848 | 2.722 / 9.992 |

У chaining промах дешевле попадания: отсутствующий ключ часто попадает в
пустую ячейку и не идёт по списку. У open addressing промах не может
остановиться на первой занятой ячейке: он обязан идти до пустой. Поэтому
именно колонка miss показывает цену загрузки.

Память при 20 000 ключах:

| представление | PHP memory | bytes/key | capacity |
|---|---:|---:|---:|
| chaining, 5 000 buckets | 3.0 MiB | 155.9 | 5 000 |
| open addressing, 32 768 slots | 1.5 MiB | 81.0 | 32 768 |
| PHP array | 1.3 MiB | 65.5 | 20 000 |

Это `memory_get_usage(false)`, а не RSS. Chaining платит за объект `Entry` на
каждый ключ; open addressing — за три параллельных массива, но без объекта
на ключ. PHP array остаётся серьёзным baseline: он уже является хеш-таблицей
и не обязан проигрывать учебной реализации.

Bloom filter при 10 000 элементах:

| target p | measured p | estimated p | bits/key | hashes |
|---:|---:|---:|---:|---:|
| 0.010 | 0.0118 | 0.0100 | 9.59 | 7 |
| 0.050 | 0.0520 | 0.0503 | 6.24 | 4 |
| 0.100 | 0.1059 | 0.1007 | 4.79 | 3 |

`measured p` — одна детерминированная выборка из 10 000 отсутствующих
запросов, а не доверительный интервал. Она близка к цели, но это не
доказательство формулы. `estimated p` — предсказание по фактическому
заполнению; `bits/key` показывает, что за меньшую вероятность платят
линейно растущим битовым массивом.

## 4. Что ломается

**Линейные пробы при высокой загрузке.** При `α = 0.90` измеренный промах
линейной таблицы — 116 проб. Простая формула `0.5 * (1 + 1/(1-α)^2)` даёт
около 50.5. Разница не означает, что сложность перестала быть `O(1)` при
фиксированном `α`; она показывает, что константа скрывает кластеризацию.
Последовательные ключи и линейный шаг создают длинные серии, и промах идёт
по всей серии.

**Память chaining.** 155.9 байта на ключ против 81.0 у open addressing — это
цена объекта на ключ. Но open addressing не бесплатен: он требует низкого
`α`, иначе пробы становятся неконтролируемыми. Выбор зависит от того, что
важнее: устойчивость к удалению и высокая загрузка или компактность.

**Bloom не является точным множеством.** Ложноположительные срабатывания
неизбежны. Нельзя проверить `mightContain()` и на основании `true` считать,
что ключ точно есть. Нельзя удалить ключ, не затронув другие. Нельзя
перечислить содержимое. Если эти операции нужны, Bloom — неподходящая
структура.

**Цель не равна измерению.** При `p = 1%` измеренное значение 1.18%, при
5% — 5.20%, при 10% — 10.59%. Это нормально для одной выборки, но в
production нужен мониторинг фактической доли ложных срабатываний, а не
только формула. Если фильтр переразмерен или недозаполнен, фактическая
вероятность будет ниже цели; если в него вставляют больше элементов, чем
ожидали, — выше.

**Качество хеш-функции зависит от ключей.** На последовательных ключах одна
функция может дать низкий chi-square, на других — нет. Эксперимент печатает
распределение по бакетам, а не объявляет победителя. Для Bloom плохая
хеш-функция увеличивает корреляцию битов и фактическую `p`.

## 5. Как это проверено

Тесты хеш-таблиц сравнивают поведение с PHP array на случайных
последовательностях `put/get/remove`, отдельно проверяют пустую таблицу,
один элемент, дубликаты, resize и надгробия. Для open addressing есть тест,
который после удаления ищет оставшиеся ключи и убеждается, что надгробие не
оборвало цепочку. Для Bloom проверяются отсутствие ложноотрицательных
ответов после вставки, формулы `m` и `k`, пустой фильтр и оценка по
фактическому заполнению.

`make check` запускает PHPUnit, PHPStan и PHP-CS-Fixer. Важная деталь:
бенчмарки не являются pass/fail-тестами. Они печатают числа и среду, но не
сравнивают время с порогом, иначе CI зависел бы от загрузки хоста. Проверка
книги отдельно сверяет каждый показанный код-блок с тегом `v1.0.0` и
диапазоном строк.

## 6. Что запомнить

- Load factor — главная переменная open addressing. При `α = 0.5` варианты
  близки, при `α = 0.9` промахи различаются на порядки.
- Chaining прощает высокую загрузку, но платит объектом на ключ. Open
  addressing компактнее, но требует запаса свободных ячеек и аккуратного
  удаления.
- Bloom filter даёт «возможно, есть» и никогда — «точно есть». Его цена —
  ложноположительные срабатывания; его преимущество — компактность и
  отсутствие хранения ключей.
- Формула Bloom предсказывает направление, а не гарантирует измеренную долю
  на конкретной выборке. Цель, оценку и наблюдение нужно хранить раздельно.
- PHP array — настоящий baseline. Если учебная структура проигрывает ему по
  памяти и скорости, это надо объяснить, а не спрятать.

4. Добавьте Counting Bloom filter с 4-битными счётчиками. Какие операции он

   подобранных ключах. Сравните chi-square и максимальный бакет. Почему
   победитель на одном наборе не обязан победить на другом?

## 8. Что дальше

Хеш-таблица отвечает на вопрос «есть ли ключ». Следующая глава добавляет
время и политику: кэш должен не только найти запись, но и решить, кого
вытеснить, когда места нет. LRU и LFU показывают, что `O(1)` на операцию и
высокий hit ratio — разные свойства. Bloom вернётся в интеграционном
сценарии, где он будет отсеивать уже виденные URL до точного подсчёта.

# Глава 5. Consistent hashing: сколько ключей переезжает

> [`v1.0.0`](https://github.com/Researcher86/algorithms-lab/releases/tag/v1.0.0).

Когда кэш или хранилище распределены по нескольким узлам, ключ нужно отобразить
на узел. Самое простое решение — `hash(key) % N`. Оно быстрое и равномерное,
пока `N` не меняется. Но стоит добавить или потерять один узел, как меняется
делитель, и почти все ключи получают нового владельца. Для кэша это означает
почти полный промах; для шардированной базы — массовое перемещение данных.

Consistent hashing решает именно эту проблему: при изменении набора узлов
переезжает только доля ключей, принадлежавших изменённому узлу, — около
`1/(N + 1)`. В главе три стратегии: modulo как baseline, кольцо с виртуальными
узлами и rendezvous-хеширование. Все три используют одну хеш-функцию, поэтому
сравнение идёт о стратегии отображения, а не о скорости хеша.

---

## 1. Проблема

Пусть есть 10 узлов и 50 000 ключей. При добавлении одиннадцатого узла идеальное
перераспределение — 9.09% ключей. Modulo меняет делитель с 10 на 11 и
перекладывает почти всё: измеренная доля 91.01%. Это не ошибка реализации; это
свойство арифметики остатков.

Нужна схема, в которой:

- добавление узла перемещает только его долю;
- удаление узла перемещает только его ключи;
- поиск остаётся дешёвым;
- нагрузка по узлам более-менее равномерна;
- можно выбрать несколько владельцев для реплик.

Кольцо решает это через токены на окружности: узел владеет интервалом до
следующего токена. Виртуальные узлы (много токенов на физический узел)
сглаживают неравномерность. Rendezvous-хеширование решает ту же задачу без
кольца: для каждого ключа считается score с каждым узлом, побеждает
максимальный.

---

## 2. Устройство

### 2.1. Modulo baseline

`ModuloHash` хранит список узлов и возвращает
`nodes[xxh128(key) % count(nodes)]`. Пока набор фиксирован, это дешёвый и
равномерный вариант. При изменении `count` почти все остатки меняются.

Modulo нужен в главе как честный baseline: он показывает, что consistent hashing
— не «более быстрый хеш», а другая функция отображения. Если узлы никогда не
меняются, modulo может быть лучшим выбором.

### 2.2. Кольцо и виртуальные узлы

`HashRing` хранит `ring[position] = node` и отсортированный список позиций.
Каждый физический узел добавляет `virtualNodes` токенов; позиция токена —
`xxh128(node . '#' . replica)`. Коллизия позиций разрешается линейным переходом
к следующей свободной позиции.

```php
    public function addNode(string $node): bool
    {
        if ($node === '') {
            throw new InvalidArgumentException('Node id cannot be empty');
        }

        if (isset($this->nodePositions[$node])) {
            return false;
        }

        $positions = [];

        for ($replica = 0; $replica < $this->virtualNodes; ++$replica) {
            $this->counters?->add('hashCalls');
            $position = Hashers::xxh128($node . '#' . $replica);

            while (isset($this->ring[$position])) {
                $position = ($position + 1) % self::SPACE;
            }

            $this->ring[$position] = $node;
            $positions[] = $position;
        }

        $this->nodePositions[$node] = $positions;
        $this->rebuildPositions();

        return true;
```

    public function getNode(string $key): ?string
    {
        if ($this->positions === []) {
            return null;
        }

Бинарный поиск по отсортированным позициям:

```php
    private function firstPositionIndexAtOrAfter(int $hash): int
    {
        $low = 0;
        $high = count($this->positions);

        while ($low < $high) {
            $middle = intdiv($low + $high, 2);
            $this->counters?->add('comparisons');

            if ($this->positions[$middle] < $hash) {
                $low = $middle + 1;
            } else {
                $high = $middle;
            }
        }

        return $low === count($this->positions) ? 0 : $low;
    }
```

[`src/ConsistentHash/HashRing.php` L166-L183](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/ConsistentHash/HashRing.php#L166-L183)

При добавлении узла появляются только его токены; ключи, которые попадали в его
интервалы, переходят к нему. Остальные интервалы не меняются. При удалении
происходит обратное. В этой реализации `addNode()` и `removeNode()` пересобирают
отсортированный список позиций, поэтому изменение стоит `O(V log V)`, где `V` —
общее число токенов. Это не асимптотика «кольца вообще», а цена конкретной
реализации; сбалансированное дерево токенов изменило бы константу.

`getNodes(key, R)` идёт по кольцу по часовой стрелке и пропускает повторных
владельцев, пока не наберёт `R` различных узлов. Это порядок fallback, а не
протокол репликации: данные никуда не копируются, отказ не обнаруживается,
физическое размещение реплик не гарантируется.

### 2.3. Rendezvous-хеширование

`RendezvousHash` для каждого ключа считает score с каждым узлом:
`xxh128(key . ':' . node)`. Побеждает максимальный score; при равенстве —
лексикографически меньший узел. Добавление узла влияет только на ключи, где
новый узел выиграл, поэтому доля перемещений близка к `1/(N + 1)`.

```php
    public function getNode(string $key): ?string
    {
        $winner = null;
        $bestScore = -1;

        foreach ($this->nodes as $node) {
            $this->counters?->add('hashCalls');
            $this->counters?->add('comparisons');
            $score = Hashers::xxh128($key . ':' . $node);

            if ($score > $bestScore || ($score === $bestScore && ($winner === null || $node < $winner))) {
                $winner = $node;
                $bestScore = $score;
            }
        }

        return $winner;
    }
```

[`src/ConsistentHash/RendezvousHash.php` L55-L72](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/ConsistentHash/RendezvousHash.php#L55-L72)

У rendezvous нет кольца и виртуальных узлов, поэтому нет пересборки токенов;
добавление и удаление в этой реализации всё равно стоят `O(N)` из-за проверки
списка узлов. Каждый поиск тоже стоит `O(N)` хешей: для 20 узлов это в несколько
раз дороже бинарного поиска по кольцу. Это законный trade-off, а не «устаревший
вариант».

## 3. Эксперимент

50 000 ключей, 10 узлов, 100 виртуальных узлов на узел. Сначала все ключи
отображаются, затем добавляется одиннадцатый узел, затем `node-0` удаляется из
кольца из одиннадцати узлов.

```bash
make experiment ARGS="ring:remap --seed=book"
```

| algorithm  | change | changed fraction | ideal |
| ---------- | ------ | ---------------: | ----: |
| modulo     | add    |           91.01% | 9.09% |
| modulo     | remove |           90.76% | 9.09% |
| ring       | add    |            9.61% | 9.09% |
| ring       | remove |           10.13% | 9.09% |
| rendezvous | add    |            9.03% | 9.09% |
| rendezvous | remove |            9.09% | 9.09% |

Идеал — доля ключей, которой владел изменённый узел, а не гарантия на каждый
запуск. Кольцо немного выше идеала из-за конечной выборки и неидеального баланса
токенов. Rendezvous ближе, потому что каждый узел получает score для каждого
ключа.

Баланс кольца, 100 000 ключей, 20 узлов:

| virtual nodes | ring size | max/mean | coefficient of variation | chi-square score |
| ------------: | --------: | -------: | -----------------------: | ---------------: |
|             1 |        20 |    1.904 |                    0.565 |        31 870.48 |
|            10 |       200 |    1.485 |                    0.276 |         7 628.24 |
|           100 |     2 000 |    1.201 |                    0.107 |         1 150.45 |
|           500 |    10 000 |    1.068 |                    0.042 |           178.88 |

Chi-square здесь — относительный score ошибки, не p-value; меньше лучше. Один
токен на узел даёт заметно неравномерное кольцо; 100 токенов снижают max/mean до
1.201, 500 — до 1.068, но кольцо вырастает до 10 000 позиций.

Реплики и отказ, 20 000 ключей, 10 узлов, 100 токенов:

|   R | average distinct owners | node coverage |
| --: | ----------------------: | ------------: |
|   1 |                    1.00 |         10/10 |
|   2 |                    2.00 |         10/10 |
|   3 |                    3.00 |         10/10 |

После удаления `node-2`:

- 2 082 ключа (10.41%) имели `node-2` первичным владельцем; ожидаемая доля была
  10.00%;
- все 2 082 перешли к старому второму владельцу;
- 17 918 ключей сохранили первичного владельца.

Это проверка порядка fallback. Она не проверяет, что второй владелец жив,
находится в другом дата-центре или получил копию данных.

Время, 20 узлов, 100 токенов:

| benchmark             | iterations |     median |   ops/sec |
| --------------------- | ---------: | ---------: | --------: |
| ring-lookup           |    100 000 |  69.049 ms | 1 448 252 |
| ring-replicas-3       |     50 000 |  50.540 ms |   989 312 |
| modulo-lookup         |    100 000 |  30.104 ms | 3 321 840 |
| rendezvous-lookup     |     50 000 | 254.973 ms |   196 098 |
| ring-add-remove       |      1 000 | 295.966 ms |     3 378 |
| modulo-add-remove     |      1 000 |   0.281 ms | 3 556 605 |
| rendezvous-add-remove |      1 000 |   0.281 ms | 3 553 445 |

Modulo — самый быстрый lookup и худший по сохранению отображений. Rendezvous
сохраняет отображения идеально, но каждый lookup хеширует все узлы; на 20 узлах
он примерно в четыре раза медленнее кольца. Кольцо пересобирает 2 000 токенов
при изменении, поэтому add/remove у него дороже; это измеренная цена реализации.

## 4. Что ломается

**Modulo при изменении `N`.** 91% перемещений — это фактически сброс кэша. Если
узлы добавляются или падают часто, modulo не подходит, даже если он самый
быстрый.

**Пересборка кольца.** `addNode()` и `removeNode()` вызывают
`rebuildPositions()`: `array_keys` + `sort`. На 2 000 токенах это заметно, на 10
000 — ещё больше. Production-кольцо может держать токены в сбалансированном
дереве и вставлять инкрементально.

**Память виртуальных узлов.** 500 токенов на 20 узлов — это 10 000 позиций.
Баланс лучше, но память и стоимость изменений растут. Выбор `virtualNodes` — это
компромисс между равномерностью и overhead.

**Rendezvous `O(N)` на lookup.** Он не хранит кольцо и идеально сохраняет доли,
но при большом числе узлов каждый запрос считает `N` хешей. Для маленького
кластера это может быть лучшим выбором; для сотен узлов — нет.

**Конечная выборка.** 9.61% и 10.13% не равны 9.09%. Это не нарушение теоремы, а
шум конечного набора ключей и неидеальный баланс токенов. Не надо подгонять
`virtualNodes` под одно наблюдение.

**Fallback не равен репликации.** `getNodes()` возвращает порядок узлов. Он не
копирует данные, не проверяет здоровье и не гарантирует, что второй узел не
находится на той же машине. Это отдельная задача.

**Нет weighted nodes и jump hash.** В главе не реализованы взвешенные узлы, jump
consistent hash и failure detection. Утверждения ограничены тем, что измерено.

## 5. Как это проверено

Тесты проверяют, что после добавления и удаления узла кольцо содержит ожидаемые
токены, `getNode()` возвращает владельца, а `getNodes(R)` — `R` различных узлов.
Для remap есть проверка доли перемещений на фиксированном наборе ключей; для
balance — что сумма долей равна единице и метрики считаются по фактическому
распределению. Modulo и rendezvous проходят те же контракты `NodeHash`.

Счётчики `hashCalls` и `comparisons` позволяют проверить, что lookup кольца
делает бинарный поиск, а rendezvous — линейный проход по узлам. `make check`
запускает тесты, PHPStan и форматтер; время не используется как порог.

## 6. Что запомнить

- Modulo — быстрый baseline, который ломается при изменении числа узлов.
- Кольцо перемещает около `1/(N + 1)` ключей; виртуальные узлы улучшают баланс,
  но увеличивают память и стоимость изменений.
- Rendezvous сохраняет ту же долю без кольца, но платит `O(N)` на lookup.
- `getNodes(R)` — порядок fallback, а не репликация.
- В этой реализации изменение кольца пересобирает отсортированный список; это
  осознанная цена, а не свойство всех колец.
- Идеал `1/(N + 1)` — математическое ожидание, а не точное число на конечной
  выборке.

## 8. Что дальше

Consistent hashing распределяет ключи по узлам. Top-K распределяет внимание: из
потока нужно выбрать самые частые элементы, не сохраняя весь поток. Следующая
глава показывает, почему точный top-K требует памяти `O(distinct)`, и что дают
ограниченные summaries.

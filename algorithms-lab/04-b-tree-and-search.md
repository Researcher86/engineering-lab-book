# Глава 4. B-дерево и B+ дерево: высота, fanout и страницы

> Проект: [`algorithms-lab`](https://github.com/Researcher86/algorithms-lab),
> тег
> [`v1.0.0`](https://github.com/Researcher86/algorithms-lab/releases/tag/v1.0.0).
> Предыдущая глава: [графы](03-graph-algorithms.md). Дальше: consistent hashing
> (глава 5).

B-дерево — это способ хранить упорядоченные ключи так, чтобы поиск стоил
небольшого числа переходов между узлами. В памяти PHP array быстрее; на диске,
где переход между узлами означает чтение страницы, решает не число сравнений, а
число страниц. В этой главе B-дерево и B+ дерево строятся целиком, а модель
страниц отделена от реального page cache, чтобы не выдавать оценки за измерения.

Главная переменная — `minimumDegree` (текстовое `t`): узел содержит не больше
`2t - 1` ключей и, кроме корня, не меньше `t - 1`. Большой `t` даёт широкие
узлы, меньшую высоту и меньше переходов, но больше работы внутри узла и больше
памяти на узел.

---

## 1. Проблема

Упорядоченный индекс должен поддерживать три операции:

- точечный поиск: есть ли ключ;
- диапазон: вернуть все ключи между `from` и `to`;
- вставку и удаление без потери упорядоченности.

Плоский отсортированный массив отвечает на поиск за `O(log n)`, но вставка и
удаление стоят `O(n)` из-за сдвига элементов. PHP array даёт быстрый точечный
поиск, но не умеет диапазон без сортировки или сканирования. B-дерево даёт
`O(log_t n)` переходов и `O(t)` работы внутри узла; B+ дерево добавляет
связанные листья, чтобы диапазон читал результаты последовательно, а не
возвращался к корню за каждым листом.

На диске узел — это страница. Если узел помещается в страницу, высота дерева
превращается в число чтений страниц. Именно поэтому `t` выбирают так, чтобы узел
был близок к размеру страницы, а не «чем больше, тем лучше».

---

## 2. Устройство

### 2.1. B-дерево

`BTree` следует семантике CLRS: `minimumDegree = t`, максимум `2t - 1` ключей.
Вставка идёт сверху вниз: если корень полон, он расщепляется, и новый корень
получает двух детей. Затем `insertNonFull()` идёт к листу и расщепляет полного
ребёнка до спуска.

```php
    public function search(int $key, ?PageSimulator $pages = null): bool
    {
        $node = $this->root;

        while (true) {
            $this->counters?->add('nodeReads');
            $pages?->readNode(count($node->keys), count($node->children));

            $index = $this->lowerBound($node, $key);

            if ($index < count($node->keys) && $node->keys[$index] === $key) {
                return true;
            }

            if ($node->leaf) {
                return false;
            }

            $node = $node->children[$index];
        }
    }

    public function insert(int $key): bool
    {
        if (count($this->root->keys) === $this->maximumKeys) {
            $newRoot = new BTreeNode(false);
            $newRoot->children = [$this->root];
            $this->root = $newRoot;
            $this->splitChild($newRoot, 0);
        }

        $inserted = $this->insertNonFull($this->root, $key);

        if ($inserted) {
            ++$this->size;
        }

        return $inserted;
    }
```

[`src/Tree/BTree.php` L49-L87](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/Tree/BTree.php#L49-L87)

При поиске на каждом узле считается `lowerBound`, затем выбирается ребёнок.
Счётчик `nodeReads` увеличивается на каждом узле, а `PageSimulator` может
зарядить одну или несколько страниц. Ключи уникальны; повторная вставка — no-op.

Удаление сложнее вставки. Если ребёнок на пути имеет `t - 1` ключей, он сначала
чинится: заимствует ключ у соседа или сливается с ним. Только после этого поиск
продолжается. Это гарантирует, что спуск не оставит узел недозаполненным. В коде
есть `borrowFromLeft`, `borrowFromRight`, `mergeChildren` и отдельная обработка
удаления внутреннего ключа через предшественника или преемника.

### 2.2. B+ дерево

`BPlusTree` хранит все ключи в листьях, а внутренние узлы — только разделители.
Разделитель — первый ключ правого ребёнка, поэтому при равенстве поиск идёт
вправо. Листья связаны через `next`, и диапазон после спуска идёт по этой
цепочке.

```php
    public function range(int $from, int $to, ?PageSimulator $pages = null): array
    {
        if ($from > $to) {
            return [];
        }

        $node = $this->root;

        while (!$node->leaf) {
            $this->counters?->add('nodeReads');
            $pages?->readNode(count($node->keys), count($node->children));
            $node = $node->children[$this->upperBound($node->keys, $from)];
        }

        $result = [];
        $first = true;

        while ($node !== null) {
            $this->counters?->add('nodeReads');
            $pages?->readNode(count($node->keys), 0);
            $start = $first ? $this->lowerBound($node->keys, $from) : 0;
            $first = false;

            for ($index = $start; $index < count($node->keys); ++$index) {
                $key = $node->keys[$index];

                if ($key > $to) {
                    return $result;
                }

                $result[] = $key;
            }

            $node = $node->next;
        }

        return $result;
```

[`src/Tree/BPlusTree.php` L164-L200](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/Tree/BPlusTree.php#L164-L200)

B+ вставка сначала вызывает `search()`, чтобы не вставлять дубликат, а затем
идёт к листу. Поэтому её счётчик `nodeReads` примерно вдвое больше, чем у
B-дерева: это цена поддержания разделителей и связанных листьев.

`bulkLoad()` собирает дерево из уже отсортированных уникальных ключей: листья
пакуются по `maximumKeys`, затем внутренние уровни строятся снизу вверх.
Последний узел уровня может быть недозаполнен; это обычный компромисс bulk load,
и `validate(false)` это допускает.

### 2.3. Модель страниц

`PageSimulator` не эмулирует операционную систему. Он оценивает размер узла по
числу ключей и детей и считает одну страницу за каждое чтение узла. Если узел
больше страницы, чтение заряжает несколько страниц. Это позволяет сравнить
«число переходов по дереву» и «число сравнений в бинарном поиске», не смешивая
разные единицы.

```php
    public function readNode(int $keys, int $children): void
    {
        $this->readBytes($this->nodeBytes($keys, $children));
    }

    public function readBytes(int $bytes): void
    {
        if ($bytes <= 0) {
            $bytes = 1;
        }

        $this->pages += intdiv($bytes + $this->pageSize - 1, $this->pageSize);
    }

    public function nodeBytes(int $keys, int $children): int
    {
        return $this->headerBytes + $keys * $this->keyBytes + $children * $this->pointerBytes;
    }
```

[`src/Tree/PageSimulator.php` L47-L64](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/Tree/PageSimulator.php#L47-L64)

Модель не знает о page cache, readahead и стоимости случайного доступа. Поэтому
её вывод узкий: дерево может превратить логарифмическое число независимых проб в
небольшое число обращений к узлам. Это не доказательство, что B-дерево всегда
быстрее массива.

Высота растёт медленно: с 50 000 до 1 000 000 ключей она увеличивается на 1–2

амортизируются. Время построения — не главный результат: оно зависит от вставок
и хоста. Число чтений узлов — устойчивый счётчик.

Шаблоны вставки, 10 000 ключей, `t = 8`:

| --------- | ---------- | -----: | --------: | ----------------: | --------: |
| BTree     | random     |      4 | 17.127 ms |              3.81 |      53.5 |
| BTree     | ascending  |      5 | 15.922 ms |              4.06 |      53.6 |
| BTree     | descending |      5 | 18.374 ms |              4.06 |      48.5 |

| BPlusTree | ascending  |      4 | 25.670 ms |              7.73 |      56.9 |
| BPlusTree | descending |      5 | 29.780 ms |              8.00 |      50.8 |
| BPlusTree | bulk load  |      4 |  0.348 ms |              0.00 |      36.5 |

Отсортированная вставка не является автоматически лучшей: она создаёт правый
край и может добавить уровень. B+ вставка делает поиск перед вставкой, поэтому
читает больше узлов. Bulk load не ищет путь и пакует листья напрямую; `0.00` в
счётчике означает, что поиск не использовался, а не что ключи не читались.

Диапазоны, 100 000 ключей, `t = 16`, 200 запросов на размер:

| result size | time/query | node reads/query | total results |
| ----------: | ---------: | ---------------: | ------------: |
|          10 |   2.255 µs |             4.29 |         2 000 |
|         100 |   5.926 µs |             7.22 |        20 000 |
|       1 000 |  43.112 µs |            36.28 |       200 000 |

Путь до листа платится один раз на запрос; дальше листья идут по `next`. Число
чтений растёт с результатом, но не повторяет корень для каждого листа. Bulk load
100 000 ключей занял 3.084 ms и 2.84 MB PHP-памяти.

Модель страниц, 100 000 ключей, `t = 16`, 1 000 поисков:

| page size | height | B-tree pages/query | binary comparisons/query | model bytes/key |
| --------: | -----: | -----------------: | -----------------------: | --------------: |
|   4 096 B |      4 |               3.95 |                    16.68 |           16.03 |
|   8 192 B |      4 |               3.95 |                    16.68 |           16.02 |

Дерево посещает около четырёх узлов, бинарный поиск делает около семнадцати
сравнений. Это разные единицы: страницы — модель I/O, сравнения — работа CPU.
Смешивать их нельзя.

потому что bulk load пакует узлы. Плоские индексы дешевле по памяти, но не дают
диапазон без сканирования или сортировки.

## 4. Что ломается

**Сортированная вставка.** Она не гарантирует лучшую форму. На 10 000 ключей
B-дерево с ascending дало высоту 5 против 4 у random. Это важно для
bulk-загрузки: если данные уже отсортированы, лучше `bulkLoad`, а не
последовательные `insert`.

**B+ вставка дороже.** Поиск перед вставкой — это не случайность, а контракт:
нужно не создать дубликат и правильно обновить разделители. Зато range-запрос
получает связанные листья.

**Bulk load и occupancy.** Последний узел уровня может быть неполным. Строгая
проверка occupancy для bulk-дерева не применяется; иначе `validate()` падал бы
на нормальном результате. Это надо явно указывать в контракте.

**B+ удаление не реализовано.** B-дерево показывает borrow/merge, но B+ удаление
требует отдельных правил для разделителей и ссылок листьев. Глава не утверждает,
что B+ write path полный.

**Модель страниц — не ОС.** 3.95 страницы на поиск не означают 3.95 физических
чтения. Page cache, readahead и Docker bind mount могут сильно изменить картину.
Модель нужна для сравнения формы, а не для прогноза latency.

**PHP array быстрее точечного поиска.** 7.976 ms на 100 000 запросов против
88.134 ms у B-дерева. Это ожидаемо: array — хеш-таблица без поддержания порядка.
B-дерево покупает диапазоны и предсказуемое число уровней, а не победу в point
lookup.

---

## 5. Как это проверено

Тесты B-дерева проверяют инварианты после каждой вставки и удаления: количество
ключей, порядок, высоту, occupancy, отсутствие дубликатов. Есть дифференциальный
тест против отсортированного массива на случайных последовательностях. Для B+
дерева проверяются связанные листья, диапазоны, поиск на границах и bulk load с
неполным последним узлом. `validate()` запускается и после вставок, и после
удалений.

Счётчики `nodeReads` сбрасываются перед поиском, чтобы построение не попадало в
число. `PageSimulator` тестируется отдельно: размер узла, округление до страниц
и `maxKeysPerPage`. `make check` запускает PHPUnit, PHPStan и форматтер;
временные бенчмарки не являются порогом.

## 6. Что запомнить

- Высота B-дерева — это `O(log_t n)`; при `t = 32` миллион ключей уложился в 4
  уровня.
- Большой `t` уменьшает число переходов, но увеличивает работу и память внутри
  узла; `t` выбирают под страницу, а не «на максимум».
- B+ дерево платит поиском при вставке, но даёт связанные листья и дешёвый
  диапазон.
- Сортированная вставка — другой паттерн, а не бесплатное ускорение.
- Модель страниц отделяет I/O от сравнений; это не эмуляция page cache.
- Плоский массив остаётся лучшим point lookup baseline; дерево нужно для порядка
  и диапазонов.

   указателях. Проверьте `PageSimulator`.
4. Постройте диапазонный запрос, который возвращает 1% ключей. Сравните B+ range
   с сортировкой всего массива.

   отличается от модели?

## 8. Что дальше

B-дерево хранит порядок на одном узле. Consistent hashing решает другую задачу:
распределить ключи по узлам так, чтобы добавление или отказ одного узла не
перекладывало почти всё. Следующая глава сравнивает modulo, кольцо с
виртуальными узлами и rendezvous-хеширование.

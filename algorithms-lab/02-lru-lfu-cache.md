# Глава 2. LRU и LFU: `O(1)` не означает «попадание»

> Проект: [`algorithms-lab`](https://github.com/Researcher86/algorithms-lab),
> тег [`v1.0.0`](https://github.com/Researcher86/algorithms-lab/releases/tag/v1.0.0).
> Предыдущая глава: [hash table и Bloom filter](01-hash-table-and-bloom-filter.md).
> Дальше: графы (глава 3).

Кэш — это не только «словарь с ограничением размера». У него есть политика
вытеснения, и именно она определяет, сколько запросов попадёт в кэш. Две
политики с одинаковой стоимостью операции могут дать совершенно разные
результаты на одном и том же потоке: LRU следует за недавностью, LFU — за
частотой. В этой главе обе реализованы на настоящих структурах, измерены на
детерминированных нагрузках и проверены на сценариях, где обе проигрывают.

Главный тезис: `O(1)` на `get()` и `put()` — это утверждение о работе с
указателями, а не о hit ratio. Кэш может быть идеально `O(1)` и при этом
промахиваться в 100% случаев.

---

## 1. Проблема

Кэш хранит ограниченное число записей. Когда место кончается, нужно выбрать
жертву. Если выбор ошибочен, следующий запрос снова идёт в медленный
источник, и кэш не выполняет свою работу. При этом сама операция выбора
должна быть дешёвой: кэш находится на горячем пути запроса.

Две классические политики:

- **LRU (least recently used)** вытесняет запись, к которой дольше всего не
  обращались. Она хорошо следует за сменой рабочего набора, но последовательный
  скан вымывает из неё всё полезное.
- **LFU (least frequently used)** вытесняет запись с наименьшей частотой.
  Она хорошо работает при стабильной популярности, но плохо реагирует на
  смену горячего набора: старые частоты никуда не исчезают.

Нужно различать три вещи:

1. **Стоимость операции** — сколько указателей и сравнений тратит `get/put`.
2. **Hit ratio** — какая доля запросов нашла данные.
3. **Память** — сколько байт на запись стоит политика.

Эта глава измеряет все три. Числа времени — один прогон на виртуализированном
Linux; форма кривых и счётчики важнее абсолютных миллисекунд.

## 2. Устройство

### 2.1. LRU: map + двусвязный список

`LRUCache` хранит `array<string, LRUNode>` для поиска за ожидаемое `O(1)` и
двусвязный список для порядка. Список имеет два sentinel-узла, `head` и
`tail`: это убирает проверки на пустой список из горячего пути. Новый элемент
вставляется после `head`, а `tail->prev` — кандидат на вытеснение.

`get()` находит узел в map, записывает hit, перемещает узел в начало списка и
возвращает значение. `put()` либо обновляет существующий узел, либо создаёт
новый и, если записей стало больше capacity, вытесняет хвост.

```php
    public function get(string $key): mixed
    {
        if (!isset($this->map[$key])) {
            $this->stats->recordMiss();

            return null;
        }

        $this->stats->recordHit();
        $node = $this->map[$key];
        $this->moveToFront($node);

        return $node->value;
    }

    public function put(string $key, mixed $value): void
    {
        if ($this->capacity === 0) {
            return;
        }

        if (isset($this->map[$key])) {
            $node = $this->map[$key];
            $node->value = $value;
            $this->moveToFront($node);

            return;
        }

        $node = new LRUNode($key, $value);
        $this->map[$key] = $node;
        $this->addAfterHead($node);

        if (count($this->map) > $this->capacity) {
            $this->evictOldest();
        }
    }
```

[`src/Cache/LRUCache.php` L49-L85](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/Cache/LRUCache.php#L49-L85)

Перемещение и удаление — это несколько операций с указателями. Счётчик
`relinks` увеличивается при каждом изменении связей; именно он, а не
секундомер, подтверждает, что работа не зависит от capacity.

```php
    private function evictOldest(): void
    {
        $oldest = $this->tail->prev;

        if ($oldest === null || $oldest === $this->head) {
            return;
        }

        $this->unlink($oldest);
        unset($this->map[$oldest->key]);
        $this->stats->recordEviction();
    }
```

[`src/Cache/LRUCache.php` L193-L204](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/Cache/LRUCache.php#L193-L204)

Важно: `isset($this->map[$key])` — это проверка наличия ключа, а не значения.
Если значение может быть `null`, `isset()` вернёт `false`, и кэш будет
считать запись отсутствующей. В этой реализации значения кэша не равны
`null`, но контракт стоит держать в голове: для произвольного `mixed` нужен
`array_key_exists()`.

### 2.2. LFU: map + bucket на каждую частоту

`LFUCache` хранит map ключей и `array<int, FrequencyBucket>`. В каждом
bucket — двусвязный список записей с одинаковой частотой. При обращении
запись переходит из bucket `f` в bucket `f + 1`. `minFrequency` указывает на
минимальную непустую частоту; именно из неё берётся жертва.

```php
    private function touch(LFUNode $node): void
    {
        $oldFrequency = $node->frequency;
        $oldBucket = $this->frequencies[$oldFrequency] ?? null;

        if ($oldBucket !== null) {
            $this->unlink($node);
            --$oldBucket->count;

            if ($oldBucket->isEmpty()) {
                unset($this->frequencies[$oldFrequency]);

                if ($this->minFrequency === $oldFrequency) {
                    ++$this->minFrequency;
                }
            }
        }

        ++$node->frequency;
        $this->addToBucket($node);
    }

    private function addToBucket(LFUNode $node): void
    {
        $frequency = $node->frequency;
        $bucket = $this->frequencies[$frequency] ??= new FrequencyBucket();
        $next = $bucket->head->next;

        if ($next === null) {
            throw new \LogicException('Frequency bucket head has no next node');
        }

        $node->prev = $bucket->head;
        $node->next = $next;
        $next->prev = $node;
        $bucket->head->next = $node;
        ++$bucket->count;
        ++$this->counters->relinks;
    }
```

[`src/Cache/LFUCache.php` L160-L198](https://github.com/Researcher86/algorithms-lab/blob/v1.0.0/src/Cache/LFUCache.php#L160-L198)

Внутри минимального bucket вытесняется хвост, то есть самая старая запись с
этой частотой. Это LRU-разрешение ничьей. Когда bucket опустел, а его
частота была минимальной, `minFrequency` увеличивается на единицу; при
удалении произвольного элемента может понадобиться пересчёт по всем
оставшимся bucket. Поэтому утверждение «LFU всегда `O(1)`» требует оговорки:
нормальный путь `get/put` с поддержанием `minFrequency` — да, но удаление
или вытеснение из опустевшего минимального bucket может стоить `O(f)`.

LFU в этой реализации **не стареет**. Запись, которая была популярна час
назад, сохраняет высокую частоту, даже если новый горячий набор уже другой.
Это не баг реализации, а свойство политики без decay. Именно поэтому
production-кэши часто используют сегментированный LRU, aging или гибрид.

### 2.3. Baseline: ArrayLRU, NaiveLRU, HeapLFU

В лаборатории есть ещё три реализации, и они нужны как baseline, а не как
декорация:

- `ArrayLRU` использует вставление-упорядоченный PHP array: удаление и
  повторная вставка ключа меняют порядок, а память близка к обычному массиву.
- `NaiveLRU` хранит список и ищет по нему линейно; это честный `O(n)` baseline,
  показывающий, что map — не бюрократия.
- `HeapLFU` хранит ленивую кучу записей на каждое обращение; старые записи
  удаляются при извлечении. Память растёт с числом обращений, а не только с
  числом ключей.

## 3. Эксперимент

Zipf-нагрузка: 100 000 возможных ключей, 20 000 запросов на ячейку,
детерминированный seed `book`. `get()` при промахе сопровождается `put()`,
как будто данные пришли из медленного источника. Hit ratio считает только
`get()`.

make experiment ARGS="cache:zipf --seed=book"

Абсолютные значения низкие, потому что 20 000 запросов не прогревают
100 000-ключевое пространство и холодные промахи входят в счёт. Сравнение

Число перелинковок ограничено числом попаданий и вставок, а не capacity. Это
косвенное подтверждение `O(1)` по указателям; время на виртуализированном
хосте слишком шумное, чтобы делать из него точный закон.

### Последовательный скан

Capacity 1 000; десять прогревающих циклов по популярному набору, затем
2 000 уникальных ключей скана, затем снова популярный набор:

| policy | warm hits | scan hits | reuse hits |
|---|---:|---:|---:|
| LRU | 90.00% | 0.00% | 0.00% |
| LFU | 90.00% | 0.00% | 99.90% |
| ArrayLRU | 90.00% | 0.00% | 0.00% |

LRU вытесняет весь популярный набор во время скана: каждый скан-ключ
оказывается самым свежим, а популярные записи уходят в хвост. LFU оставляет
почти всё, потому что скан-ключи входят с частотой 1 и не могут обогнать
старые частоты. Потеря 0.10% — это первая вставка скана, которой пришлось
кого-то вытеснить.

### Смена популярности

Набор A горячий, затем B, затем A снова; по 1 000 ключей, по десять циклов:

| policy | A first | B next | A returns |
|---|---:|---:|---:|
| LRU | 100.00% | 90.00% | 90.00% |
| LFU | 100.00% | 0.00% | 99.99% |
| ArrayLRU | 100.00% | 90.00% | 90.00% |

Это зеркало скана. LFU не забывает A: старые частоты выше, чем у B, поэтому B
не может стать резидентным. LRU следует за B и платит при возврате A. Обе
картины нормальны; вопрос в том, какая из них ближе к вашей нагрузке.

### Циклический скан

Capacity 100, один прогрев, затем пять измеряемых циклов:

| loop length | LRU | LFU | ArrayLRU |
|---:|---:|---:|---:|
| 99 | 100.00% | 100.00% | 100.00% |
| 100 | 100.00% | 100.00% | 100.00% |
| 101 | 0.00% | 0.00% | 0.00% |
| 200 | 0.00% | 0.00% | 0.00% |

Цикл длины `capacity + 1` — классический worst case LRU: каждый запрос
вытесняет ключ, который понадобится следующим. LFU не помогает, потому что у
всех ключей одинаковая частота, и LRU-разрешение ничьей даёт тот же порядок.
Это самый короткий пример того, что `O(1)` не гарантирует hit ratio.

### Память и время

При 10 000 записях и capacity, равной числу записей:

| представление | PHP memory | bytes/entry |
|---|---:|---:|
| LRU | 1.84 MiB | 192.5 |
| LFU | 1.87 MiB | 196.2 |
| HeapLFU | 3.10 MiB | 325.4 |
| ArrayLRU | 0.64 MiB | 66.6 |
| NaiveLRU | 3.85 MiB | 403.9 |
| PHP array | 0.62 MiB | 65.5 |

Это PHP-аллокатор, не RSS. LRU и LFU платят за map и объект узла; HeapLFU —
ещё и за запись на каждое обращение. ArrayLRU близок к обычному массиву,
потому что использует его же упорядоченность.

## 4. Что ломается

**Скан вымывает LRU.** Это не редкий случай: резервное копирование, обход
таблицы, холодный отчёт — всё это последовательности, которые не должны
становиться самыми популярными. LRU без защиты от скана может уничтожить
hit ratio на минуты.

**LFU не забывает.** При смене популярности старые тяжёлые ключи остаются в
кэше, а новый набор не может набрать частоту. Нужен decay, окно или
сегментация. В таблице `B next` у LFU 0.00% — это не ошибка измерения, а
свойство политики.

**Цикл `capacity + 1` ломает обе.** Он показывает, что политика, идеальная
на одном распределении, может быть худшей на другом. Кэш надо проверять на
своём потоке, а не выбирать по названию.

**LFU и `O(1)`.** `minFrequency` поддерживается на нормальном пути, но
опустевший bucket и удаление могут потребовать сканирования. В отчёте об
алгоритме это надо писать явно, а не обещать «строго O(1) всегда».

**HeapLFU растёт с accesses.** Ленивая куча не чистит старые записи сразу;
при долгом горячем ключе память может расти, пока записи не будут извлечены.
Это цена более простого `decrease-key`-подобного поведения.

**ArrayLRU — не политика.** Он совпадает с LRU по hit ratio в этом
эксперименте, но использует insertion order PHP array. Это отличный baseline
и иногда практичный выбор, но он не даёт отдельного контроля над памятью и
не является универсальной заменой LRU.

## 5. Как это проверено

`ArrayLRU` и `NaiveLRU` служат дифференциальными моделями: на случайных
последовательностях `get/put/remove` их состояние сравнивается с LRU.
Тесты проверяют пустой кэш, capacity 0, один элемент, обновление
существующего ключа, вытеснение, hit/miss/eviction counters и отсутствие
утечки узлов. Для LFU отдельно проверяются переходы между bucket,
`minFrequency`, удаление из середины и LRU-разрешение ничьей.

Счётчик `relinks` даёт проверяемое свойство: на попадании число изменений
связей ограничено константой, а не capacity. `make check` запускает тесты,
PHPStan и форматтер. Бенчмарк печатает числа, но не используется как
time-threshold: иначе CI зависел бы от соседей по хосту.

## 6. Что запомнить

- LRU и LFU — разные гипотезы о будущем, а не «быстрый» и «медленный» кэш.
- LRU следует за недавностью и ломается на скане; LFU следует за частотой и
  ломается на смене популярности.
- `O(1)` относится к работе с указателями; hit ratio зависит от нагрузки.
- Цикл `capacity + 1` — обязательный тест для любой политики вытеснения.
- ArrayLRU — серьёзный PHP-baseline; связанный список не автоматически
  быстрее.
- Без decay или сегментации LFU не является улучшением LRU «по умолчанию».

## 7. Упражнения

1. Реализуйте segmented LRU (как в Redis): protected и probationary сегменты.
   Проверьте на скане и смене популярности. Как изменился reuse hit rate?
2. Добавьте к LFU aging: периодически уменьшайте все частоты или храните
   окно. Найдите режим, где выигрывает и скан, и смена популярности.
3. Реализуйте CLOCK (second-chance) и сравните память и hit ratio с LRU на
   тех же четырёх нагрузках.
4. Измерьте `relinks` для ArrayLRU. Почему он равен нулю и что это скрывает?
5. Постройте нагрузку, на которой HeapLFU выигрывает у LRU по hit ratio, но
   проигрывает по памяти. Объясните, какой ресурс вы бы ограничили в
   production.

## 8. Что дальше

Кэш отвечает на вопрос «кого вытеснить». Графы добавляют вопрос «как
представить связи между объектами, чтобы не платить за них квадратично».
В следующей главе одно и то же множество рёбер загружается в список,
матрицу, список рёбер и CSR; разница в памяти и числе чтений видна до
любых рассуждений о big-O.

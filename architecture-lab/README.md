# Книга Architecture Lab

> Статус: **7 глав готовы**. Код закреплён тегом
> [`v1.0.0`](https://github.com/Researcher86/architecture-lab/releases/tag/v1.0.0).

Учебник по архитектуре backend-приложения, написанный по коду лаборатории
[`architecture-lab`](https://github.com/Researcher86/architecture-lab). Каждая
глава разбирает один архитектурный механизм на настоящем PHP-коде, показывает
эксперимент, числа и зависимости, а затем явно перечисляет, что осталось за
пределами измерения.

Это не каталог паттернов и не спор «монолит против микросервисов». Лаборатория
отвечает на вопрос «что здесь реализовано и чем это проверено», а книга — на
вопрос «почему граница устроена так, сколько она стоит и где ломается».

## Что вы сможете

Книга рассчитана на PHP-разработчика, который уже писал код и хочет разобраться
в архитектурных границах на уровне, достаточном для чтения и изменения системы.
После неё вы сможете:

- отличить слоистую архитектуру как направление зависимостей от набора папок
  `Controller`, `Service`, `Repository` и увидеть layer skip в импортах;
- объяснить, что покупает порт, что стоит замена адаптера и почему in-memory
  реализация не доказывает атомарность;
- проверить правило зависимостей автоматически: сканер, граф, циклы и метрики
  модулей, а не только договорённость на ревью;
- удержать модульный монолит от превращения в общую модель: `PublicApi`,
  anti-corruption адаптеры и цена границы в бенчмарке;
- разделить команды и запросы, построить проекцию из событий и измерить окно
  устаревания read model;
- собрать outbox в одной транзакции с агрегатом, пережить повторную доставку и
  честно назвать границу идемпотентности;
- разложить один сценарий на пять bounded contexts с разными агрегатами,
  языками и контрактами и проверить их согласованность инвариантами;
- читать числа экспериментов вместе с окружением и счётчиками, а не как
  универсальный рейтинг архитектур.

## Как читать

Главы идут в фиксированном порядке: каждая использует идеи предыдущих. Полный
маршрут — читать 1–7 подряд. Если механизм уже знаком, главу можно пропустить,
но ссылки «→ глава N» показывают, где он разбирается.

Стандартная глава устроена так:

1. **Проблема** — какой отказ архитектуры рассматривается.
2. **Устройство** — как механизм реализован, с выдержками из кода.
3. **Эксперимент** — что запустить, чтобы увидеть механизм живым.
4. **Что ломается** — ограничения, failure modes и честные оговорки.
5. **Как это проверено** — тесты, счётчики и инварианты.
6. **Что запомнить** — сжатый итог.
7. **Упражнения** — задачи на понимание и измерение.

Выдержки кода скопированы из файлов как есть и снабжены ссылкой на GitHub с
диапазоном строк. Ссылки привязаны к тегу `v1.0.0`, а не к ветке `master`,
поэтому номера строк не «уплывут» после следующих коммитов. Комментарии в коде
лаборатории на английском; книга на русском.

Сквозной сценарий из главы 7 запускается одной командой `make scenario`:
публикация двух курсов → 12 запросов на зачисление → резервирование мест →

проверяет 11 инвариантов, включая `stale-before-pump`, `capacity-conserved`,
`catalog-conserved` и `notifications-match`.

## Как запустить

Все команды выполняются в Docker-контейнере проекта; на хост не нужно ставить
PHP или расширения. Если репозиторий лаборатории лежит рядом с книгой:

```bash
cd ../../architecture-lab
make build install      # один раз
make check              # PHPUnit + PHPStan + PHP-CS-Fixer
make experiment         # список экспериментов
make scenario           # интеграционный сценарий
```

Полный список экспериментов и бенчмарков — в `make experiment` и
`make benchmark`; измеренные таблицы с окружением лежат в
[`docs/BENCHMARKS.md`](https://github.com/Researcher86/architecture-lab/blob/v1.0.0/docs/BENCHMARKS.md).
Числа в главах — один прогон в Docker на виртуализированном Linux, а не
универсальная константа. Сравнивайте форму кривых, счётчики и зависимости, а не
только миллисекунды.

## Проверка книги

Каждый показанный код-блок сверяется с закреплённым тегом и диапазоном строк;
все GitHub-ссылки проверяются на существование файла и валидность диапазона;
локальные ссылки README должны резолвиться. Из каталога книги:

```bash
python3 ../php-systems-lab/tools/check_book.py \
  --expected-chapters=7 \
  --source-root ../..
```

`--source-root ../..` читает локальные репозитории без сети и ожидает структуру
`<repo>/<path>`, то есть `engineering-lab/architecture-lab/...`. В CI тот же
checker запускается с `--expected-chapters=7` для Architecture Lab, с обычными 26
главами для PHP Systems Lab и с `--expected-chapters=7` для Algorithms Lab.

## Что не обещается

- Это не рейтинг архитектур. Числа зависят от PHP, Docker, хоста и fixture;
  в главах указано, где именно сделан один прогон.
- Это не production-система: SQLite в одном процессе, синхронная in-memory шина,
  без HTTP, брокера, аутентификации и конкурентной нагрузки.
- Это не exactly-once: outbox даёт at-least-once, а `IdempotentListener`
  оставляет окно между side effect и записью ключа.
- Это не полноценный DDD-проект: агрегаты не записывают события сами, а
  `Shared` содержит общие идентификаторы и деньги.
- Это не модель распределённых транзакций: пять контекстов делят одну базу, и
  границы здесь — границы кода, а не операционные границы.
- Это не замена архитектурному проектированию: checker видит `use`-импорты, но
  не динамические имена классов, SQL и подписки на события.
